# 파일 업로드 네트워크 재시도·멱등성 정책 결정

> 문서 상태: ADR 결정 전 검토 원문
> 결정 상태: ADR 0015에서 핵심 책임 분리 원칙 채택. 세부 API·운영 값은 미결정.

## 결정해야 하는 것

파일을 로컬 서버 파일시스템에 저장하는 동기 업로드에서 네트워크 오류가 발생했을 때 FE가 자동 재시도할지, 재시도 중복을 막기 위해 `Idempotency-Key`를 사용할지 결정한다.

이 결정은 FE의 요청 상태와 사용자 안내뿐 아니라 업로드 API 계약, 파일 저장 결과의 조회·복구 방식, 키와 결과의 영속성, 동시 요청 처리에 영향을 준다.

## 현재 사실과 공통 규칙

- `POST /api/v1/files`는 multipart 파일을 검증한 뒤 서버 생성 파일명으로 `./uploads`에 저장하고 `201 Created`를 반환한다.
- 성공 응답에는 저장 파일명과 완료 메시지가 포함된다.
- 입력 오류와 확장자 차단은 명시적인 4xx 응답으로 확인할 수 있다.
- 네트워크 오류나 응답 타임아웃은 서버가 파일 저장을 완료했는지 FE가 알 수 없는 상태다.
- 현재 API에는 업로드 작업 ID, 결과 조회 API, `Idempotency-Key` 계약이 없다.
- 서버 생성 UUID 파일명만으로는 같은 논리적 업로드의 재시도 여부를 알 수 없다.

모든 선택지는 다음 규칙을 만족해야 한다.

1. 같은 논리적 업로드의 자동 재시도는 같은 멱등성 키를 사용한다.
2. 별개의 사용자의 업로드나 사용자의 새 업로드는 새로운 키를 사용한다.
3. 같은 키로 다른 파일을 보내면 원래 요청과 다른 요청으로 조용히 처리하지 않는다.
4. 명시적인 4xx 응답은 자동 재시도하지 않는다.
5. 키 검증만으로는 충분하지 않으며, 서버가 키와 처리 결과를 재사용할 수 있어야 한다.
6. 파일시스템 쓰기와 키·결과 기록은 하나의 ACID 트랜잭션이 아니므로 중간 장애와 고아 파일 처리 방식을 별도로 정의한다.

## 멱등키 구성 제안

### 키 자체

FE가 Web Crypto의 `crypto.randomUUID()`로 UUID v4를 생성한다. 키에는 파일명, 사용자 ID, 시각, 확장자, 파일 해시를 조합하지 않는다.

```http
POST /api/v1/files
Idempotency-Key: 5f0d8d7e-4b7b-4c1d-9b2c-2e5d9a4f81a6
```

UUID는 사람이 의미를 해석하는 값이 아니라 충돌 가능성이 낮은 불투명 식별자여야 한다. 파일명이나 사용자 ID를 포함하면 개인정보·키 재사용·문자열 정규화 문제를 만들고, 파일 해시만 사용하면 사용자가 같은 파일을 의도적으로 두 번 업로드하는 동작까지 하나로 합칠 수 있다.

### UUID만으로 충분한 범위

UUID v4는 **키의 형식과 충돌 방지 수단으로는 충분**하다. UUID v7의 정렬 가능성은 보존·조회 편의에는 도움이 될 수 있지만 멱등성 자체를 더 강하게 만들지는 않는다.

반대로 UUID만 생성하고 서버가 이를 저장하지 않으면 멱등성은 보장되지 않는다. 서버가 매 요청마다 새 UUID 파일명을 만들기 때문에, 같은 `Idempotency-Key`를 보내도 서버가 이전 요청을 모르는 경우 파일이 중복 생성될 수 있다.

따라서 보장은 다음 세 요소의 결합으로 정의한다.

```text
random client UUID
+ server-persisted key/result record
+ request fingerprint validation
```

클라이언트 UUID는 인증 토큰이나 비밀값도 아니다. 클라이언트가 키를 임의로 재사용하거나 다른 파일에 붙일 수 있으므로, 서버는 키의 길이·형식·범위와 요청 지문을 검증해야 한다.

### 키의 생성·유지 시점

- 사용자가 업로드 버튼을 누르는 **논리적 업로드 시작 시점**에 한 번 생성한다.
- 네트워크 오류, 타임아웃, 수동 재시도에서는 기존 키를 유지한다.
- 업로드가 성공하거나 명시적으로 실패하면 해당 키를 종료한다.
- 같은 파일을 새로 업로드하려는 사용자의 별도 행동에는 새 키를 생성한다.
- 페이지 새로고침 후에도 같은 작업을 이어가야 한다면 키와 파일 선택 상태를 복구할 별도 UX가 필요하다. 그렇지 않으면 새 업로드로 취급한다.

```text
사용자 업로드 시작       → K1 생성
1차 HTTP 요청            → K1
응답 타임아웃            → K1 유지
자동 재시도              → K1
성공 응답 수신            → K1 종료
같은 파일을 새로 업로드  → K2 생성
```

### 서버의 멱등성 식별자

저장 키는 헤더 값 하나만으로 구성하지 말고, 요청을 처리하는 경계와 함께 묶는다.

```text
idempotency_identity = scope + HTTP method + route + Idempotency-Key
```

인증이 도입되면 `scope`는 사용자 또는 테넌트 식별자로 정한다. 현재 인증이 없는 단일 업로드 API에서는 route와 키의 unique 조합으로 시작할 수 있다. 서버는 키 원문을 파일명이나 저장 경로로 사용하지 않는다.

### 요청 지문

같은 키가 다른 요청에 재사용되지 않았는지 서버가 확인할 수 있도록 요청 지문을 함께 저장한다. 현재 API에서는 최소한 다음을 서버에서 계산하는 방안을 검토한다.

```text
request_fingerprint = SHA-256(file bytes) + normalized final extension
```

원본 파일명이 향후 사용자 표시 메타데이터가 되면 그 값도 요청 의미에 포함할지 별도로 결정한다. FE가 보내는 해시나 지문은 최적화 힌트일 뿐이며, 서버의 최종 검증을 대신하지 않는다.

### 권장 저장 형태

```text
scope
route
idempotency_key       UNIQUE(scope, route, idempotency_key)
request_fingerprint
status                 PROCESSING | SUCCEEDED | FAILED
stored_filename
response_status
response_snapshot
created_at
expires_at
```

`SUCCEEDED`인 키가 다시 오면 저장 파일을 새로 만들지 않고 기존 결과를 반환한다. `PROCESSING` 중인 동일 키의 처리는 대기·`202`·`409` 중 하나를 정해야 하며, 지문이 다른 요청은 `409`로 거부하는 것이 안전하다.

## 동일 키의 `PROCESSING` 처리

`PROCESSING`은 최종 실패 예외가 아니라 아직 결과가 정해지지 않은 중간 상태다. 두 번째 요청이 이 상태를 발견했다고 해서 새 파일 저장을 시작하면 안 되고, 첫 번째 처리의 결과를 기다리거나 나중에 같은 키로 다시 확인해야 한다.

### 권장 흐름

```text
1차 요청 K1
→ DB에서 K1을 원자적으로 PROCESSING으로 선점
→ 임시 파일 저장

2차 요청 K1
→ PROCESSING 확인
→ 파일 저장을 시작하지 않음
→ 202 + operationId + Retry-After 반환

1차 처리 완료
→ K1을 SUCCEEDED로 변경하고 storedFilename·응답 저장

FE 재조회/재시도
→ K1의 저장된 성공 결과 반환
```

현재처럼 동기 `POST /files` 계약을 유지하려면 2차 요청이 짧게 기다린 뒤, 제한 시간 안에 끝나지 않을 때 `202 Accepted`를 반환하는 방식이 적합하다. 결과 조회 API를 당장 추가하지 않는다면 대안으로 `409 IDEMPOTENCY_KEY_IN_PROGRESS`와 `Retry-After`를 반환할 수 있지만, 이 경우 FE가 같은 키로 다시 요청하는 계약이 필요하다. 이 `409`는 영구 실패가 아니라 재시도 가능한 충돌로 분류해야 한다.

### 영원히 `PROCESSING`에 머물지 않게 하는 장치

멱등성 기록에는 처리 소유자와 lease 만료 정보를 둔다.

```text
status: PROCESSING
owner_token
lease_until
attempt_version
```

- 정상 처리 중인 요청은 lease를 갱신한다.
- `lease_until`이 지나면 새 요청이 즉시 두 번째 저장을 시작하지 않고, stale 복구 절차가 해당 기록을 `ABANDONED` 또는 `FAILED_RETRYABLE`로 전환한다.
- 복구된 재처리는 새 임시 파일과 새 attempt version을 사용한다.
- 최종 성공 변경은 현재 attempt version과 일치할 때만 허용해 늦게 끝난 이전 요청이 결과를 덮어쓰지 못하게 한다.
- 최종 파일은 임시 파일을 원자적으로 이동해 만들고, 실패한 attempt의 임시 파일은 정리한다.

처리 시간보다 짧은 lease를 사용하면 정상적인 대용량 업로드가 stale로 오판될 수 있으므로, lease 길이와 최대 업로드 처리 시간을 함께 정해야 한다. 더 높은 복구 신뢰성이 필요하면 업로드 요청과 파일 저장을 분리한 비동기 작업 모델로 전환하고, `GET /uploads/{operationId}`에서 상태를 조회하게 하는 편이 명확하다.

### FE의 종료 조건

FE도 무한 재시도를 하지 않는다.

- `202` 또는 `IDEMPOTENCY_KEY_IN_PROGRESS`를 받으면 `Retry-After`를 따른다.
- 같은 키로 재시도하되, 전체 대기 기한을 둔다.
- 기한을 넘기면 `UNKNOWN` 또는 `결과 확인 필요`로 표시하고 사용자의 새 행동을 기다린다.
- 사용자가 같은 논리적 업로드를 계속 확인하는 동안에는 키를 바꾸지 않는다.

이 구조에서 “예외를 던지지 않는다”는 것은 무조건 성공 처리한다는 뜻이 아니다. `PROCESSING`이라는 상태를 정상적인 프로토콜 응답으로 표현하고, 서버와 FE 모두 유한한 대기·복구 규칙을 갖는다는 뜻이다.

## 재시도 횟수와 업로드 파일 상태의 분리

FE가 `Retry-After`를 따라 세 번 재요청했다는 사실과 서버가 파일 저장을 세 번 시도했다는 사실은 다르다. 따라서 `clientRetryCount`와 `storageAttemptCount`를 같은 값으로 사용하지 않는다.

```text
FE의 관찰 재시도 3회
→ 화면은 UNKNOWN 또는 결과 확인 필요
→ 서버의 PROCESSING 작업은 계속 완료될 수 있음
→ 완료된 결과는 같은 키의 후속 요청에 재사용
```

`FileUpload`가 영속 파일 자체를 의미한다면 FE 재시도 횟수를 그 엔티티의 `FAILED` 전이 조건으로 사용하지 않는 편이 안전하다. 필요하다면 멱등성 기록 또는 업로드 작업에 다음처럼 별도 관측 정보를 남긴다.

```text
client_observation_count
storage_attempt_count
last_observed_at
```

### 비동기 삭제의 범위

FE 재시도 횟수가 최대치에 도달했다는 이유만으로 최종 저장 파일을 삭제하면 안 된다. 응답이 유실됐을 뿐 실제 저장은 성공했을 수 있기 때문이다. 삭제는 다음처럼 서버가 실패를 확정할 수 있는 대상에만 비동기로 수행한다.

- 저장 중 실패한 임시 파일
- lease가 만료되고 복구 절차에서 버려진 임시 파일
- `FAILED` 또는 `ABANDONED`로 확정된 작업에 연결된 파일
- 메타데이터가 없고 유예 기간이 지난 고아 파일

반대로 `SUCCEEDED` 또는 결과가 아직 확정되지 않은 최종 파일은 멱등키 보존 기간 동안 유지한다. 비동기 삭제는 작업 큐가 없어도 초기에는 주기적 정리 작업으로 구현할 수 있지만, 삭제 대상·재시도·중복 실행에 안전해야 한다.

### 권장 상태 전이

```text
RECEIVING
  ├─ 저장 성공 → STORED
  ├─ 일시적 저장 실패 → FAILED_RETRYABLE → 같은 키 재처리
  └─ owner lease 만료 → ABANDONED → 임시 파일 정리

FE 재시도 한도 초과
  └─ 서버 상태를 FAILED로 바꾸지 않음
     → 화면만 UNKNOWN으로 종료
```

서버가 실제 작업을 비동기로 수행하는 모델이라면 `FileUpload`와 `UploadOperation`을 분리하는 편이 더 명확하다. `UploadOperation`은 멱등키·처리 상태·재시도·lease를 관리하고, `FileUpload`는 최종 저장된 파일 메타데이터만 표현한다.

## 타임아웃·`Retry-After`·실패 시점의 분리

“넉넉한 파일 저장 타임아웃이 지나면 실패 처리” 자체는 이상하지 않다. 다만 다음 세 가지 시간을 하나로 사용하지 않는다.

```text
storage deadline      서버가 한 번의 저장 작업을 허용하는 최대 시간
retry-after           다음 상태 확인 또는 재요청까지 기다릴 시간
client overall limit  FE가 자동 확인을 계속할 최대 시간
```

`Retry-After`는 서버가 후속 요청까지 기다리기를 바라는 시간을 나타내는 헤더이며, 초 단위 지연 또는 HTTP 날짜로 표현할 수 있다. 따라서 대용량 파일 저장의 전체 타임아웃을 `Retry-After` 값으로 그대로 보내기보다, 현재 상태를 다시 확인할 수 있는 짧은 간격으로 사용하는 편이 적절하다. [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html#section-10.2.3)은 이 헤더를 후속 요청 전 대기 시간으로 정의한다.

권장 예시는 다음과 같다.

```text
서버 저장 deadline: 10분      // 파일 저장 작업의 상한
PROCESSING 응답: 202 또는 409
Retry-After: 2                // 2초 후 상태 확인
FE 자동 확인: 최대 3회 또는 전체 30초
```

여기서 FE가 3회 확인을 마쳤다고 서버 작업을 곧바로 `FAILED`로 만들면 안 된다. 실제 저장 작업은 계속 실행 중이거나 이미 성공했을 수 있기 때문이다. FE는 화면을 `UNKNOWN`으로 종료하고, 서버는 자신의 deadline·lease·owner 상태로 작업을 판정해야 한다.

서버 deadline이 지나면 바로 최종 파일을 삭제하기보다 다음 순서가 안전하다.

1. 현재 owner가 살아 있는지 확인한다.
2. 처리 중이면 `ABANDONED` 전환을 보류하거나 owner가 종료하도록 한다.
3. lease 만료와 작업 중단이 확인되면 `FAILED_RETRYABLE` 또는 `ABANDONED`로 전환한다.
4. 임시 파일을 비동기로 삭제한다.
5. 최종 파일·성공 메타데이터가 이미 존재하면 즉시 삭제하지 않고 멱등키 보존 기간 동안 결과로 재사용한다.

정말 비동기 작업으로 전환한다면 `202 Accepted`와 상태 조회 URI를 함께 제공하는 편이 HTTP 의미에 맞다. `202`는 요청을 접수했지만 처리가 아직 끝나지 않았음을 뜻하며, 상태 조회 리소스가 있어야 사용자가 최종 결과를 확인할 수 있다. [RFC 9110의 202 정의](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.3.3)도 이 응답을 완료되지 않은 처리에 사용하도록 설명한다.

실무 API의 한 사례처럼, 서버가 첫 요청의 상태 코드와 응답 본문을 멱등키에 저장하고 같은 키의 후속 요청에 같은 결과를 반환하는 방식도 가능하다. 다만 동시 처리 중인 요청은 별도 충돌로 재시도하게 하고, 요청 파라미터가 달라지면 오류로 처리해야 한다. [Stripe의 멱등 요청 문서](https://docs.stripe.com/api/idempotent_requests)는 이 패턴과 UUID v4 키, 요청 파라미터 비교를 설명하지만, 저장소·보존 기간은 서비스 특성에 맞게 결정해야 한다.

### 피해야 할 구성

| 구성 | 문제 |
|---|---|
| `userId + filename` | 같은 파일의 의도적 중복 업로드를 막고 개인정보가 노출될 수 있음 |
| `timestamp + filename` | 시계·정규화·동시성에 의존하고 키 충돌 가능성이 남음 |
| 파일 SHA-256만 사용 | 같은 내용의 별도 업로드를 구분하지 못함 |
| FE 키를 저장 파일명으로 직접 사용 | 사용자 입력이 저장 경로 의미에 영향을 줌 |
| HTTP 요청마다 새 UUID 생성 | 재시도마다 새 작업으로 인식되어 멱등성이 깨짐 |

## 선택지 A: FE 자동 재시도 + 서버 멱등성 기록

### 구조 예시

```text
IdempotencyRecord
- scope: 사용자·테넌트·API 범위
- key: Idempotency-Key
- request_fingerprint: 파일 내용·크기·확장자 등의 요청 지문
- status: PROCESSING | SUCCEEDED | FAILED
- stored_filename: 성공 시 서버 저장 파일명
- response_snapshot: 성공 응답에 필요한 값
- created_at, expires_at
```

`scope + key`에 unique 제약을 두고, 성공 결과와 저장 파일명을 기록한다. 같은 키의 재요청은 성공 결과를 다시 반환하고, 다른 요청 지문이면 충돌 오류를 반환한다.

### 동작 예시

```text
1차 요청: Idempotency-Key: K1
서버: report.pdf 저장 후 응답 직전 연결 종료
FE: K1을 유지한 채 자동 재시도
서버: K1의 SUCCEEDED 결과를 찾아 같은 filename 응답 재전달
결과: 파일 1개, FE는 성공 확정
```

처리 중인 동일 키가 동시에 들어오면 기존 요청이 끝날 때까지 기다리거나 `202`와 결과 조회 경로를 반환하는 정책이 추가로 필요하다. 단순 구현에서는 중복 요청을 `409 IDEMPOTENCY_KEY_IN_PROGRESS`로 거부하고 FE가 같은 키로 다시 조회·재시도할 수 있다.

### 장점

- 응답 유실 후 같은 요청을 재전송해도 중복 결과를 줄일 수 있다.
- 서버가 원래 성공 응답을 보존하므로 별도의 파일명 추측이나 목록 검색이 필요 없다.
- 자동 재시도와 수동 재시도의 의미를 동일한 키로 통합할 수 있다.
- 향후 다중 서버로 확장할 때도 공유 DB나 전용 저장소를 통해 정책을 유지할 수 있다.

### 단점과 실패 모드

- 키 기록 저장소와 만료·정리 정책이 필요하다.
- 파일시스템과 DB 기록 사이의 장애 구간이 남는다. 파일 저장 후 프로세스가 종료되기 전에 성공 기록을 남기지 못하면 고아 파일이나 재처리 판단 문제가 생길 수 있다.
- 같은 키 요청의 동시성, 다른 파일 재사용, 처리 중 만료를 정의해야 한다.
- 요청 지문 계산은 큰 파일에서 비용이 들 수 있다. multipart 전체 해시 대신 크기·정규화 확장자·콘텐츠 해시의 사용 범위를 결정해야 한다.

### 영향

- API: `Idempotency-Key` 요청 헤더와 키 충돌·처리 중 응답 계약이 추가된다.
- 저장: 키와 저장 파일명·응답 결과를 영속화할 테이블 또는 저장소가 필요하다.
- 테스트: 응답 유실, 같은 키 재요청, 다른 본문 재사용, 동시 요청, 만료 후 재요청을 검증해야 한다.
- 운영: 키 보존 기간, 개인정보·파일 내용의 로그 제외, 저장 결과와 idempotency record 정합성 모니터링이 필요하다.

## 선택지 B: 키를 저장 파일 식별자에 결정적으로 반영

### 구조 예시

FE가 키를 만들고 서버가 키에서 파생한 서버 식별자로 저장 경로를 결정한다. 같은 키와 같은 확장자는 같은 최종 경로를 사용한다.

```text
Idempotency-Key K1 + normalized extension txt
→ server-derived storage name S(K1, txt)
→ uploads/S(K1, txt)
```

재시도 시 같은 경로에 새로 쓰므로 파일이 여러 개 생기는 문제를 줄인다. 키 원문을 파일명으로 직접 사용하지 않고 서버에서 안전한 식별자로 파생해야 한다.

### 동작 예시

```text
1차 요청 K1: uploads/S1.txt에 저장 중 연결 종료
재시도 K1: uploads/S1.txt를 다시 처리
결과: 최종 경로는 하나
```

### 장점

- 별도 idempotency 결과 테이블 없이 중복 최종 파일명을 줄일 수 있다.
- 저장 결과와 파일 경로의 관계가 단순하다.
- 로컬 단일 서버 과제에서는 구현 요소가 적다.

### 단점과 실패 모드

- 기존 파일이 완전한 파일인지 부분 파일인지 저장 경로만으로 확정하기 어렵다.
- 첫 요청이 성공했지만 응답이 유실된 경우에도 서버가 성공 응답 본문을 복원할 수 없다.
- 키 만료, 다른 요청 본문 재사용, 처리 중 동시 요청을 별도로 검증해야 한다.
- 사용자 제어 키가 저장 경로 의미에 직접 영향을 주면 경로·충돌·재사용 위험이 생긴다. 파생 식별자와 요청 지문 검증이 필요하다.
- 파일 덮어쓰기 허용 여부와 원자적 임시 파일 교체 정책이 필수다.

### 영향

- API: 요청 헤더는 필요하지만 결과 조회나 응답 snapshot은 제공하지 않는다.
- 저장: 결정적 파일명, 임시 파일, 원자적 교체 규칙이 필요하다.
- 테스트: 부분 파일, 재시도 중 프로세스 종료, 동일 키의 다른 파일, 동시 저장을 검증해야 한다.
- 운영: 파일만 보고 성공·실패를 구분하기 어렵고, 고아·부분 파일 정리 기준이 별도 필요하다.

## 선택지 C: 자동 재시도 없이 결과 불확실 상태와 수동 재시도만 제공

### 구조 예시

FE는 네트워크 오류를 `업로드 결과 확인 불가`로 표시하고 자동으로 다시 보내지 않는다. 사용자가 재시도하면 새로운 업로드로 처리한다.

### 동작 예시

```text
업로드 요청 후 응답 유실
→ FE: 결과를 확인할 수 없다고 표시
→ 사용자: 다시 업로드 선택
→ 서버: 새 UUID 파일을 생성
```

### 장점

- API와 서버 저장 구조를 거의 변경하지 않는다.
- 자동 재시도로 인한 요청 폭주를 피한다.
- 사용자가 중복 업로드 가능성을 인지하고 선택할 수 있다.

### 단점과 실패 모드

- 사용자가 재시도하면 중복 파일이 생길 수 있다.
- 네트워크가 일시적으로 불안정해도 사용자가 직접 복구해야 한다.
- 결과 불확실 상태를 해결하지 못하고 사용자에게 판단을 넘긴다.

### 영향

- API: 새로운 계약이 거의 없다.
- UX: 자동 복구가 없고, 중복 가능성을 안내해야 한다.
- 테스트·운영: 서버의 멱등성 상태를 추가하지 않는 대신 중복 업로드와 문의 대응 절차가 남는다.

## 비교 요약

| 기준 | A. 서버 멱등성 기록 | B. 결정적 파일 식별자 | C. 수동 재시도 |
|---|---|---|---|
| 중복 방지 강도 | 높음 | 중간 | 낮음 |
| 성공 응답 복원 | 가능 | 제한적 | 불가 |
| 파일시스템 장애 대응 | 별도 보완 필요 | 별도 보완 필요 | 현재와 동일 |
| API·DB 복잡도 | 높음 | 중간 | 낮음 |
| 단일 서버 과제 적합성 | 요구 수준에 따라 선택 | 제한적으로 적합 | 가장 단순 |
| 다중 서버 확장성 | 높음 | 저장 경로 공유 필요 | 낮음 |

## 결정 결과

핵심 원칙은 [ADR 0015](../adr/0015-separate-upload-retry-idempotency-and-state.md)에서 채택했다. FE 재시도 횟수, 멱등키 재사용, 서버 업로드 상태, 확정된 실패 파일 정리의 책임을 분리한다. `Retry-After` 값, 처리 중 응답의 구체적인 HTTP 상태, lease와 보존 기간의 숫자는 후속 API·운영 결정으로 남긴다.

## 결정 전 추천 의견

검토 의견으로는 **선택지 A를 장기 방향으로 추천**한다. 다만 현재 업로드가 단순 동기 저장이고 업로드 결과 조회·메타데이터가 아직 없다면, 처음부터 완전한 exactly-once를 약속하기보다 다음 단계로 나누는 편이 안전하다.

1. FE는 하나의 논리적 업로드 시도마다 UUID 키 하나를 생성한다.
2. 네트워크 오류와 연결 타임아웃에 한해 짧은 횟수로 자동 재시도한다.
3. 자동 재시도와 사용자의 같은 작업 재시도에는 동일한 키를 사용한다.
4. 명시적 4xx는 재시도하지 않는다.
5. 서버는 키를 받아도 영속적으로 결과를 기억하지 않는 동안에는 중복 방지가 보장되지 않는다고 문서화한다.
6. 보장을 도입할 때 `IdempotencyRecord` 또는 `UploadFile` 메타데이터에 키·요청 지문·처리 상태·저장 파일명을 함께 기록한다.

자동 재시도 횟수를 소진한 뒤에는 “업로드 실패”라고 단정하기보다 “업로드 결과를 확인하지 못했습니다. 다시 시도할 수 있습니다.”라고 표시하는 것이 적절하다. 서버가 `SUCCEEDED` 결과를 재생할 수 있게 된 이후에는 같은 키 재요청을 성공 응답으로 복원한다.

## 결정 전에 확인할 질문

- 네트워크 오류 시 자동 재시도를 허용할 최대 횟수와 총 대기 시간은 얼마인가?
- `500 FILE_UPLOAD_FAILED`처럼 응답을 받은 서버 오류도 자동 재시도할 것인가?
- 같은 키로 다른 파일을 보낸 경우 응답 상태와 오류 코드는 무엇인가?
- 키를 사용자·세션·테넌트 중 어느 범위로 격리할 것인가?
- 키와 성공 결과를 얼마 동안 보존할 것인가?
- 처리 중인 동일 키 재요청은 대기, `202`, `409` 중 어떤 방식으로 처리할 것인가?
- 파일 저장 후 키 기록 전 프로세스가 종료된 경우 고아 파일을 어떻게 판정하고 정리할 것인가?
