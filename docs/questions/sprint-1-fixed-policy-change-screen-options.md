# 스프린트 1 고정 확장자 변경 화면 선택지 검토 원문

> 문서 상태: ADR 결정 배경 원문
>
> 결정 상태: [ADR 0002](../adr/0002-resynchronize-fixed-policy-after-patch-failure.md)로 결정 완료
>
> 관련 문서: [스프린트 1 API 계약](../sprints/sprint-1-file-upload-api.md), [스프린트 1 구현 완료 체크리스트](../sprints/sprint-1-file-upload-checklist.md)

## 1. 왜 추가 결정이 필요한가

고정 확장자 PATCH API는 이미 구현되어 있지만 조회 화면의 체크박스는 읽기 전용이다. 화면 연동 범위, PATCH 실패 뒤 화면 상태를 복구하는 방법, 프런트 상호작용의 검증 도구를 정해야 API 상태와 화면이 달라지는 상황을 피할 수 있다.

## 2. 구현 범위 선택지

### 선택지 A: PATCH 화면 연동만 구현

- 장점: 이미 구현된 API를 사용해 체크·해제와 새로고침 유지라는 한 가지 사용자 흐름에 집중할 수 있다.
- 단점: 변경된 정책이 실제 파일 업로드를 허용하거나 거부하는 검증은 후속 단계에 남는다.
- 영향: 체크박스와 상태 메시지만 변경하고 파일 업로드 API·저장소는 건드리지 않는다.

### 선택지 B: 파일 업로드까지 함께 구현

- 장점: 정책 변경부터 실제 업로드 판정까지 한 번에 검증할 수 있다.
- 단점: multipart 계약, 파일 저장 위치와 이름, 무확장자 정책까지 함께 결정해야 하므로 작업 범위가 크게 늘어난다.
- 영향: 화면 변경 외에 새로운 API, 저장 기능, 보안 검증이 필요하다.

## 3. PATCH 실패 복구 선택지

### 선택지 A: 클릭 전 상태로 즉시 복원

- 장점: 추가 네트워크 요청이 없고 구현이 단순하다.
- 단점: 서버가 변경을 적용한 뒤 응답만 유실된 경우 DB 상태와 화면이 달라질 수 있다.
- 예시: `exe` 차단 요청의 응답이 끊기면 화면은 해제 상태로 돌아가지만 DB에는 차단 상태가 남을 수 있다.

### 선택지 B: 전체 정책 재조회

- 장점: 실패 원인이 불확실해도 GET 결과로 fixed와 custom 화면을 DB의 최신 상태에 맞출 수 있다.
- 단점: 실패 뒤 GET 요청이 한 번 더 발생하며, 재조회도 실패하는 경우를 별도로 처리해야 한다.
- 예시: `exe` PATCH가 실패하면 전체 정책을 다시 받아 모든 체크박스와 커스텀 목록을 재렌더링한다.

### 선택지 C: 사용자가 시도한 상태 유지

- 장점: 사용자가 같은 상태로 다시 요청하기 쉽다.
- 단점: 저장에 실패한 값을 화면에 남겨 DB 상태로 오해하게 만들 수 있다.

## 4. 프런트 검증 선택지

### 선택지 A: 현재 도구 유지

- 장점: Gradle 중심의 현재 프로젝트에 새 Node 패키지나 테스트 실행 체계를 추가하지 않는다.
- 단점: JavaScript 상호작용은 실제 브라우저 smoke 검증 근거가 필요하다.

### 선택지 B: JavaScript DOM 단위 테스트 도입

- 장점: 체크박스와 Axios 오류 흐름을 자동화할 수 있다.
- 단점: DOM 테스트 라이브러리와 별도 실행 구성이 필요하다.

### 선택지 C: 브라우저 E2E 테스트 도입

- 장점: 실제 사용자 흐름을 가장 강하게 자동 검증한다.
- 단점: 브라우저 설치, 실행 시간, 테스트 유지 비용이 이번 단계에 비해 크다.

## 5. 사용자 결정

- 구현 범위는 **PATCH 화면 연동만** 포함한다.
- PATCH 실패 시 **전체 정책을 재조회**한다. 재조회도 실패하면 클릭 전 상태를 복원하고 새로고침 안내를 표시한다.
- **현재 테스트 도구를 유지**하고 기존 MockMvc·통합 테스트와 실제 브라우저 smoke로 검증한다.
- 하나의 PATCH 또는 실패 복구가 끝날 때까지 모든 고정 확장자 체크박스를 잠가 동시 변경 경합을 막는다.
