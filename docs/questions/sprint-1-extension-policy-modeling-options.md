# 스프린트 1 확장자 정책 모델링 선택지 검토 원문

> 문서 상태: ADR 결정 전 검토 원문
>
> 결정 상태: 미결정
>
> 관련 문서: [스프린트 1 API 계약](../sprints/sprint-1-file-upload-api.md), [스프린트 1 구현 완료 체크리스트](../sprints/sprint-1-file-upload-checklist.md), [스프린트 1 단일 커밋 작업 순서](../sprints/sprint-1-file-upload-single-commit-sequence.md)

## 1. 이 문서에서 결정해야 하는 것

파일 업로드 확장자 정책을 다음 중 어떤 모델로 관리할지 결정이 필요하다.

1. 고정 확장자와 커스텀 확장자를 각각의 엔티티로 저장한다.
2. 고정·커스텀을 하나의 엔티티에서 유형 또는 상태로 관리한다.
3. 고정 확장자는 코드 카탈로그로, 커스텀 확장자는 DB 엔티티로 관리하는 혼합 모델을 사용한다.
4. 하나의 도메인 개념 아래 별도 저장 모델을 두고 애플리케이션 서비스에서 통합한다.

이 결정은 확장자 중복을 DB에서 보장할 수 있는지, 정책 조회가 얼마나 단순한지, fixed/custom별 규칙을 어디에 둘지, 향후 정책 속성을 추가할 때 어떤 변경이 필요한지를 좌우한다.

## 2. 현재 구현 사실

현재 작업 브랜치에는 1~3단계 진행 결과로 다음 구조가 존재한다.

- `FixedExtensionPolicy`: 고정 확장자와 `blocked` 상태를 저장한다.
- `CustomExtensionPolicy`: 커스텀 확장자 존재 자체를 차단 정책으로 저장한다.
- `FixedExtensionPolicyRepository`, `CustomExtensionPolicyRepository`: 별도 저장소를 사용한다.
- `ExtensionNormalizer`: 앞뒤 공백 제거, 소문자 변환, 빈 값·20자 초과·점 포함 입력을 검증한다.
- 고정 확장자 기본 목록은 `FixedExtensionCatalog`에서 제공한다.
- 고정 확장자 초기화는 누락된 기본 항목만 DB에 추가하고 기존 차단 상태를 보존한다.

위 구조는 현재 구현 사실이며, 이 문서는 해당 구조를 최종 설계로 확정하지 않는다.

## 3. 공통 도메인 규칙

모든 선택지는 아래 API 계약과 행동을 만족해야 한다.

- 고정 확장자는 `bat`, `cmd`, `com`, `cpl`, `exe`, `scr`, `js` 7개다.
- 고정 확장자는 체크·해제할 수 있고 상태는 DB에 유지된다.
- 커스텀 확장자는 최대 200개, 이름은 최대 20자다.
- 확장자는 앞뒤 공백을 제거하고 소문자로 비교한다.
- 커스텀 목록에는 고정 확장자가 노출되지 않는다.
- 동일한 정규화 확장자는 중복 등록되지 않는다.
- 파일 업로드 판정은 fixed/custom 저장 상태를 함께 사용한다.
- API 응답은 fixed 상태와 custom 목록이라는 기존 JSON 계약을 유지한다.

## 4. 선택지 A: fixed/custom을 각각의 엔티티로 관리

### 구조 예시

```text
p_fixed_extension_policy
- id
- extension
- blocked

p_custom_extension_policy
- id
- extension
```

고정 확장자는 행의 `blocked` 값으로 상태를 표현하고, 커스텀 확장자는 행이 존재하면 차단된 것으로 해석한다.

### 동작 예시

- `exe` 고정 정책: `p_fixed_extension_policy(extension='exe', blocked=true)`
- `sh` 커스텀 정책: `p_custom_extension_policy(extension='sh')`
- 사용자가 `exe`를 커스텀으로 추가하려 하면 고정 저장소를 먼저 조회해 거부한다.
- 업로드 `script.EXE`는 파일 확장자를 `exe`로 정규화한 뒤 고정 저장소의 `blocked`를 확인한다.

### 장점

- fixed와 custom의 업무 의미가 엔티티 구조에 직접 드러난다.
- 고정 확장자만 상태를 가지며 커스텀 확장자는 존재 여부로 차단하는 규칙을 자연스럽게 표현한다.
- fixed 목록과 custom 목록의 API 응답 형태를 각각의 저장 모델에서 바로 조립할 수 있다.
- 향후 fixed와 custom에 서로 다른 속성이나 생명주기가 생겨도 각 엔티티에 독립적으로 추가할 수 있다.
- 현재 구현과 가장 가까워 변경 범위가 작다.

### 단점과 주의점

- 두 테이블에 `extension`이 나뉘므로 fixed와 custom 사이의 중복을 하나의 DB unique 제약으로 막을 수 없다.
- 커스텀 추가 시 두 저장소를 모두 조회해야 한다.
- 업로드 차단 판정 시 fixed/custom 저장소를 각각 조회하거나 통합 서비스가 두 결과를 합쳐야 한다.
- 삭제·조회·중복 검증 코드가 두 엔티티에 나뉘어 유사해질 수 있다.
- 동시 요청에서 두 저장소 사이 중복을 막으려면 서비스 트랜잭션과 추가 방어가 필요하다.

## 5. 선택지 B: 하나의 엔티티에서 유형과 상태를 관리

### 구조 예시

```text
p_extension_policy
- id
- extension unique
- policy_type: FIXED | CUSTOM
- blocked
```

하나의 확장자 정책 엔티티가 `policy_type`으로 fixed/custom을 구분한다. fixed는 `blocked`를 변경하고, custom은 생성·삭제로 차단 여부를 표현할 수 있다.

### 동작 예시

- `exe` 고정 정책: `(extension='exe', policy_type='FIXED', blocked=true)`
- `sh` 커스텀 정책: `(extension='sh', policy_type='CUSTOM', blocked=true)`
- `exe`를 커스텀으로 추가하면 `extension unique` 제약 또는 사전 조회로 중복을 거부한다.
- 업로드 `script.EXE`는 하나의 저장소에서 `extension='exe'` 정책을 조회하고 `blocked`를 확인한다.

### 장점

- `extension`에 전역 unique 제약을 둘 수 있어 fixed/custom 간 중복을 DB 수준에서 직접 방어할 수 있다.
- 저장소와 업로드 차단 판정이 하나로 단순해진다.
- 중복 조회, 정책 존재 여부, 확장자별 단일 정책 조회가 한 모델로 통일된다.
- 향후 공통 속성인 등록 시각, 차단 사유, 정책 출처를 한 곳에 추가하기 쉽다.

### 단점과 주의점

- custom은 존재 자체가 차단이라는 규칙과 `blocked` 필드가 동시에 있어 잘못된 상태 조합이 생길 수 있다.
- 예를 들어 `policy_type=CUSTOM, blocked=false`가 저장되지 않도록 도메인 검증이 필요하다.
- fixed 전용 기본 목록과 custom 전용 최대 개수·삭제 규칙이 하나의 엔티티에 섞인다.
- API용 fixed 배열과 custom 문자열 배열을 만들 때 `policy_type`별 분기 조립이 필요하다.
- 현재 분리된 엔티티와 저장소를 하나로 합치는 마이그레이션이 필요하다.

## 6. 선택지 C: 고정은 코드 카탈로그, 커스텀만 DB 엔티티로 관리

### 구조 예시

```text
FixedExtensionCatalog: bat, cmd, com, cpl, exe, scr, js

p_custom_extension_policy
- id
- extension unique
```

고정 확장자 이름은 enum 또는 불변 코드 목록으로 관리하고, 차단 상태는 별도의 설정 저장소나 애플리케이션 설정에 둔다. 커스텀 확장자만 DB에 저장한다.

### 동작 예시

- 코드 카탈로그가 `exe`의 존재를 보장한다.
- `exe`의 차단 상태를 DB에 유지하려면 `fixed_extension_state` 같은 별도 상태 테이블이 추가로 필요하다.
- `sh`는 custom 테이블에 존재하면 차단된다.

### 장점

- 고정 확장자의 이름과 개수가 코드에서 명확하게 고정된다.
- 사용자가 고정 확장자 자체를 추가·삭제할 수 없는 정책을 강하게 표현한다.
- 커스텀 데이터만 DB에서 관리하므로 커스텀 CRUD가 단순하다.

### 단점과 주의점

- 고정 확장자의 체크·해제 상태를 새로고침 후 유지해야 하므로 코드 목록만으로는 API 계약을 충족할 수 없다.
- 결국 고정 상태용 별도 테이블 또는 key-value 설정 저장소가 필요해져 구조가 두 갈래로 나뉜다.
- fixed/custom 중복 검증을 위해 코드 카탈로그와 DB를 함께 조회해야 한다.
- 환경별 설정 파일에 차단 상태를 두면 사용자가 변경한 상태를 DB에 유지한다는 요구와 충돌할 수 있다.

## 7. 선택지 D: 하나의 도메인 개념과 별도 저장 모델을 서비스에서 통합

### 구조 예시

```text
ExtensionPolicyService
 ├─ FixedExtensionPolicyRepository
 └─ CustomExtensionPolicyRepository

도메인 관점에서는 ExtensionPolicy로 통합
저장 관점에서는 fixed/custom 테이블을 유지
```

엔티티를 즉시 하나로 합치지 않고, 애플리케이션 서비스가 두 저장소를 감싼다. API와 업로드 판정은 서비스만 호출하도록 한다.

### 동작 예시

- 커스텀 `sh` 추가 시 서비스가 정규화 → 고정 저장소 중복 확인 → 커스텀 저장소 개수·중복 확인 → 저장한다.
- 정책 조회 시 서비스가 fixed와 custom을 각각 조회해 API 응답 모델로 조립한다.
- 업로드 `exe` 판정 시 서비스가 fixed 정책을 우선 조회하고, 없으면 custom 정책을 조회한다.

### 장점

- 현재 두 엔티티 구조를 유지하면서 API·업로드 판정의 호출 지점을 하나로 만들 수 있다.
- 엔티티의 저장 책임과 정책의 업무 규칙을 분리할 수 있다.
- 향후 단일 테이블로 변경하더라도 컨트롤러와 FE 계약의 변경을 줄일 수 있다.
- 테스트가 API 사용 사례 중심으로 작성되며 저장소 교체 영향을 서비스 아래로 숨길 수 있다.

### 단점과 주의점

- 두 테이블의 전역 중복 제약 문제는 서비스와 트랜잭션에 계속 남는다.
- 서비스가 두 저장소의 조회·저장 순서와 실패 처리를 모두 책임져야 한다.
- 도메인 개념은 하나인데 영속 모델은 둘이어서 처음 보는 개발자에게 구조 설명이 필요하다.
- 단순한 기능에 서비스 조합 계층이 과하다고 느껴질 수 있다.

## 8. 엔티티 모델과 별도로 정할 검증 책임 컨벤션

현재 `ExtensionNormalizer`는 `domain` 패키지에 있으며 정규화와 유효성 검증을 한 메서드에서 수행한다. 유사한 입력 검증 책임이 늘어날 경우 다음 선택지가 있다.

### 검증 책임 선택지 1: `validator` 패키지와 `Validator` 접미사

```text
com.example.demo.domain.validator.ExtensionValidator
```

`ExtensionValidator`가 입력의 공백·대소문자·길이·점 포함 여부를 검증하고 정규화 결과를 반환한다.

- 장점: 검증 책임 객체를 한 패키지에서 찾기 쉽고 클래스명만으로 책임을 알 수 있다.
- 장점: `FilenameValidator`, `UploadRequestValidator`처럼 유사 책임의 명명 규칙을 확장하기 쉽다.
- 단점: 정규화가 단순 검증을 넘어 확장자 값 자체의 도메인 규칙이라면 validator 패키지가 도메인 의미를 약하게 표현할 수 있다.
- 예시: `ExtensionValidator.normalize(" EXE ")`는 `exe`를 반환하고, `ExtensionValidator.normalize("tar.gz")`는 예외를 반환한다.

### 검증 책임 선택지 2: 현재처럼 도메인 공통 유틸리티 유지

```text
com.example.demo.domain.ExtensionNormalizer
```

- 장점: 현재 코드 변경이 없고 호출이 짧다.
- 장점: 정규화라는 동작 이름이 검증보다 정확한 경우 의미가 분명하다.
- 단점: 검증 객체가 늘어나면 `domain` 패키지에 책임이 섞일 수 있다.
- 예시: 엔티티 factory가 `ExtensionNormalizer.normalize(input)`을 호출해 저장 가능한 문자열을 얻는다.

### 검증 책임 선택지 3: 값 객체로 책임 이동

```text
com.example.demo.domain.ExtensionName
```

`ExtensionName.create(" EXE ")`가 정규화와 검증을 수행하고, 엔티티는 유효한 값 객체만 받는다.

- 장점: 확장자라는 도메인 값의 유효성·동일성·정규화를 한 곳에 모을 수 있다.
- 장점: 엔티티와 업로드 판정이 문자열 처리 규칙을 직접 알지 않아도 된다.
- 단점: JPA 컬럼 매핑을 위해 `@Embeddable` 또는 converter가 필요하다.
- 단점: 현재 문자열 필드 중심 모델보다 코드와 테스트 구조가 커진다.
- 예시: `ExtensionName.create(" EXE ").value()`는 `exe`를 반환하고, 서로 다른 입력이 같은 값 객체로 정규화된다.

## 9. 비교 요약

| 기준 | A. 별도 엔티티 | B. 단일 엔티티 | C. 코드 카탈로그+DB | D. 서비스 통합 |
|---|---|---|---|---|
| 현재 코드 변경량 | 작음 | 큼 | 중간 이상 | 작음~중간 |
| fixed/custom 전역 중복 DB 보장 | 어려움 | 쉬움 | 어려움 | 어려움 |
| fixed/custom 규칙 분리 | 명확함 | 조건 분기 필요 | 분리됨 | 서비스에서 분리 |
| 단일 정책 조회 | 두 저장소 조합 | 단일 조회 | 복합 조회 | 서비스에서 통합 |
| API 조립 | 저장 모델과 유사 | 유형 분기 필요 | 복합 조회 | 서비스가 조립 |
| 미래 공통 속성 추가 | 중복 가능 | 쉬움 | 저장 위치 분산 | 서비스·모델 검토 필요 |
| 현재 구현과의 연속성 | 높음 | 낮음 | 낮음 | 높음 |

## 10. 결정 전 추천 의견

### 엔티티 모델 추천 후보

현재 스프린트의 범위와 이미 작성된 구현을 기준으로는 다음 두 안이 우선 검토 대상이다.

1. **A안: 별도 엔티티 유지**
   - fixed는 상태 변경, custom은 존재·삭제라는 차이를 코드에서 명확히 유지할 수 있다.
   - 현재 구현을 크게 되돌리지 않고 다음 REST/API 단계로 진행할 수 있다.
   - 대신 서비스 계층에서 fixed/custom 전역 중복과 동시 요청을 방어해야 한다.

2. **B안: 단일 엔티티로 재설계**
   - 확장자 하나에 하나의 정책만 존재한다는 핵심 제약을 DB unique로 직접 표현할 수 있다.
   - 업로드 판정과 중복 검증이 단순해진다.
   - 대신 유형별 규칙의 잘못된 상태를 엔티티가 방어해야 하고 현재 구현을 마이그레이션해야 한다.

현재 원문 기준의 추천 후보는 **A안에 D안의 통합 서비스 책임을 결합하는 방식**이다. 이유는 fixed/custom의 의미 차이와 현재 코드 연속성을 보존하면서, 컨트롤러가 두 저장소를 직접 조합하지 않도록 경계를 만들 수 있기 때문이다. 다만 fixed/custom 전역 unique 제약이 최우선이면 B안이 더 적합할 수 있다.

이 문단은 검토 우선순위를 제시하는 추천 의견이며, 최종 결정이 아니다.

### 검증 책임 컨벤션 추천 후보

입력 검증 책임 객체가 계속 늘어날 것으로 판단되면 `domain.validator.ExtensionValidator`와 `Validator` 접미사 컨벤션을 우선 검토한다. 확장자 정규화가 독립된 도메인 값으로 발전하면 `ExtensionName` 값 객체로 승격하는 안을 재검토한다.

## 11. 결정 전에 확인할 질문

- fixed와 custom 사이의 동일 확장자 중복을 DB 제약으로 반드시 보장해야 하는가?
- fixed와 custom에 앞으로 서로 다른 속성·상태·권한이 추가될 가능성이 있는가?
- 현재 스프린트에서 구조 마이그레이션 비용보다 API 구현 속도가 중요한가?
- 업로드 판정의 단일 조회와 저장소 단순성이 별도 엔티티의 의미 분리보다 중요한가?
- 확장자 검증 규칙이 향후 파일명·업로드 요청 검증과 공유될 것인가?
- 공유된다면 `validator` 패키지와 `Validator` 접미사를 적용할 것인가, 아니면 확장자 값 객체로 승격할 것인가?
- 위 질문에 대한 답변을 ADR에 어떤 선택과 근거로 기록할 것인가?

## 12. ADR 전환 조건

다음이 합의된 뒤에만 이 문서를 ADR로 전환한다.

- 엔티티·테이블 모델 선택
- fixed/custom 전역 중복을 보장하는 위치
- 정책 서비스의 통합 책임 범위
- 검증 책임 객체의 패키지와 클래스명 규칙
- 현재 구현을 유지할지 마이그레이션할지
