# 업로드 상태를 먼저 저장하고 파일은 임시 경로에서 원자적으로 확정한다

## 배경

업로드 메타데이터를 DB에 저장하고 실제 파일을 로컬 파일시스템에 저장하는 작업은 하나의 ACID 트랜잭션으로 묶을 수 없다. 파일을 먼저 저장하면 DB에 기록되지 않은 고아 파일이 생길 수 있고, 최종 경로에 직접 쓰면 복사 중 프로세스가 종료될 때 부분 파일이 최종 파일처럼 남을 수 있다.

업로드 완료 여부를 응답만으로 표현하면 응답 유실이나 프로세스 중단 이후 서버가 어떤 상태에 있는지 복구하기 어렵다. 따라서 DB에 업로드 처리 상태를 먼저 기록하고, 파일 저장과 완료 상태를 분리해 관리해야 한다.

## 결정

- `UploadFile` 메타데이터는 파일 저장 전에 `RECEIVING` 상태로 DB에 저장한다. `requestId`는 `Idempotency-Key`와 같은 논리적 업로드 식별자이며 unique 제약을 둔다.
- 입력 검증과 확장자 정책 판정에 실패한 요청은 `UploadFile` 레코드와 물리 파일을 생성하지 않는다.
- `RECEIVING` 저장 트랜잭션은 파일 I/O 전에 커밋한다. 파일 저장이 끝날 때까지 DB 트랜잭션을 열어 두지 않는다.
- 실제 파일은 최종 경로가 아닌 같은 파일시스템의 임시 경로에 동기적으로 쓴다.
- 임시 파일 쓰기가 성공한 뒤 임시 경로에서 최종 경로로 atomic move를 수행한다. 최종 경로에는 완성된 파일만 나타나야 한다.
- 최종 파일 확정 후 별도의 DB 트랜잭션에서 `UploadFile` 상태를 `COMPLETED`로 변경한다.
- `COMPLETED` 상태 변경이 커밋된 뒤에만 업로드 성공 응답 `201 Created`를 반환한다.
- 파일 저장 실패 시 임시 파일 삭제를 시도하고 `FAILED` 상태를 기록한다. 프로세스 중단으로 상태 변경이 실행되지 않은 `RECEIVING` 레코드는 복구·정리 대상이다. `RECEIVING`이 30분 이상 갱신되지 않으면 stale로 판단하고 1분 주기 정리 작업에서 최종 파일 존재 여부를 확인한 뒤 `COMPLETED` 또는 `FAILED`로 확정한다.
- 파일 조회·다운로드와 같은 후속 기능은 `COMPLETED` 상태의 레코드만 정상 파일로 취급한다. `RECEIVING`과 `FAILED` 상태의 파일은 외부에 제공하지 않는다.

DB 상태와 파일시스템은 여전히 하나의 원자적 트랜잭션이 아니므로, 이 결정은 exactly-once 처리나 응답 유실 후 중복 업로드 방지까지 보장하지 않는다. 재시도 멱등성, 업로드 결과 조회, 상태별 보존 기간은 별도 결정으로 둔다.

## 처리 흐름

```text
입력·정책 검증
  → UploadFile(RECEIVING) DB 커밋
  → 임시 경로에 동기 파일 저장
  → atomic move로 최종 경로 확정
  → UploadFile(COMPLETED) DB 커밋
  → 201 Created 응답
```

파일 저장이나 최종 상태 변경이 실패하면 성공 응답을 반환하지 않는다. 최종 파일은 존재하지만 `COMPLETED` 상태 변경이 실패한 경우에도 해당 레코드는 `RECEIVING` 상태로 남을 수 있으며, 복구 작업은 레코드와 파일의 존재·무결성을 대조해 완료 처리 또는 실패·정리를 수행한다.

## 고려한 대안

### 최종 경로에 직접 쓰고 완료 상태를 변경

임시 파일과 move가 없어 구현은 단순하다. 그러나 복사 중 장애가 발생하면 최종 경로에 부분 파일이 남고, 파일 경로만 확인하는 운영·복구 로직이 부분 파일을 완성 파일로 오인할 수 있다.

### 파일을 먼저 저장한 뒤 DB 메타데이터를 생성

메타데이터가 저장되기 전까지는 사용자에게 파일을 노출하지 않을 수 있지만, 파일 저장 후 프로세스가 종료되면 DB에서 추적할 수 없는 고아 파일이 된다. 업로드 처리 상태와 복구 대상이 명시되지 않는다는 단점이 있다.

### 비동기 업로드 작업으로 전환

파일 저장을 요청 처리와 분리하고 `202 Accepted`와 작업 상태 조회를 사용할 수 있다. 대용량 파일이나 외부 스토리지에는 적합하지만, 현재의 동기 업로드 요구보다 상태 머신·조회 API·재처리 운영이 커진다.

## 결과

- DB가 업로드 처리 상태의 기준이 되므로 미완료 업로드를 조회·복구·정리할 수 있다.
- 최종 경로에는 완성 파일만 노출되어 부분 파일 위험이 줄어든다.
- 파일 저장이 요청 처리 안에서 완료된 뒤 성공 응답을 반환하므로 현재 동기 업로드 API와 호환된다.
- DB 커밋과 파일시스템 변경 사이의 장애 구간은 남으므로 `RECEIVING` stale 정리와 파일 무결성 확인이 필요하다.
- DB 트랜잭션이 파일 I/O 시간만큼 점유되지 않아 대용량 업로드가 DB 커넥션을 불필요하게 오래 잡지 않는다.
- 응답 유실 후 동일 요청의 중복 저장은 ADR 0015의 requestId 기반 결과 재사용으로 처리한다.

## 범위 제외

- 업로드 결과 조회 API
- 외부 오브젝트 스토리지 및 비동기 바이러스 검사
- 파일 내용의 내구성 보장을 위한 `fsync` 운영 정책

## 기존 결정과의 관계

이 ADR은 서버 생성 파일명과 로컬 저장 위치를 정한 [ADR 0003](0003-server-generated-file-storage-policy.md)과 `UploadFile` 메타데이터를 정의한 [ADR 0006](0006-persist-upload-file-name-mapping.md)을 보완한다. 업로드 오류의 로그 추적 식별자는 [ADR 0013](0013-use-request-id-and-frontend-owned-upload-messages.md)의 `requestId` 정책을 따른다.
