# 정책 변경 이력을 운영 원인 추적 기록으로 보존

## 배경

`ExtensionPolicy`의 현재 행은 현재 차단 상태와 최종 수정 시각을 보여주지만, 정책이 어떤 순서로 변경되었는지는 보존하지 않는다. 특히 커스텀 정책은 물리 삭제되므로 삭제된 정책은 현재 테이블에서 존재 사실까지 사라진다.

운영 중 업로드 장애나 보안 사고가 발생하면 다음을 구분할 수 있어야 한다.

- 운영자가 정책을 변경한 것인지 내부 로직이 잘못 변경한 것인지
- 정책이 삭제된 것인지, 삭제 후 다시 등록된 것인지
- 장애 시점에 정책이 어떤 상태였는지
- 정책 변경과 장애가 시간상 연관되어 있는지

`updatedAt`만으로는 마지막 수정 시각만 알 수 있고, 일반 애플리케이션 로그는 장기 보존·무결성·변경 전후 상태를 보장하는 감사 기록으로 사용할 수 없다.

## 결정

- 정책 생성, 고정 정책 차단 상태 변경, 커스텀 정책 삭제와 같은 상태 변경을 별도 append-only 정책 이력 테이블에 기록한다.
- 이력에는 이벤트 시각, 대상 정책 식별 정보, 변경 동작, 변경 전 값과 변경 후 값, 변경 경로와 요청 식별자를 보존한다.
- 인증된 주체가 존재하는 경우 actor를 기록하고, 인증이 없는 시스템 동작은 `SYSTEM` 등 시스템 주체로 구분한다. 인증 전에는 IP나 추정값을 실제 사용자의 신원처럼 기록하지 않는다.
- 정책 현재 상태 변경과 이력 기록은 같은 트랜잭션 경계에서 처리한다. 정책만 변경되거나 이력만 남는 상태를 정상적인 변경 결과로 허용하지 않는다.
- 현재 정책의 물리 삭제 정책은 유지한다. 삭제 이벤트를 이력에 남겨 삭제 후 재등록과 신규 등록을 구분할 수 있도록 한다.
- 이력은 운영 원인 추적을 위한 데이터로 사용하며, 업로드 파일 이력·일반 디버깅 로그·파일 원본을 대신하지 않는다.

## 결과

- 정책 변경의 시간 순서와 변경 전후 상태를 복원할 수 있다.
- 운영자는 정책 변경, 삭제 후 재등록, 시스템 초기화 동작을 구분해 장애 원인을 좁힐 수 있다.
- 현재 행을 soft delete로 바꾸지 않아도 삭제 사실을 보존할 수 있다.
- 정책 변경마다 이력을 남겨야 하므로 새로운 변경 경로나 DB 직접 쓰기가 추가될 때 기록 누락 여부를 검토해야 한다.
- 이 결정은 과거에 이미 발생한 변경을 복원하지 못한다. 이력 도입 이후의 변경부터 추적할 수 있다.
- 인증·인가가 도입되기 전에는 변경 주체를 개인 단위로 특정할 수 없으며, actor 기록은 시스템 주체와 변경 경로 수준으로 제한된다.

## 검토한 대안

- `createdAt`·`updatedAt`만 유지하는 방식은 구현이 작지만 중간 변경, 삭제, 변경 전 상태를 복원할 수 없어 운영 원인 추적 요구를 충족하지 못한다.
- soft delete는 삭제 행을 보존할 수 있지만 최신 조회 조건과 재등록 시 unique 정책을 복잡하게 만든다. 별도 이력 테이블로 현재 상태 모델과 이력 모델을 분리한다.
- 일반 로그만 남기는 방식은 검색에는 유용하지만 정책의 변경 전후 상태와 장기 보존·무결성을 보장하는 계약으로 삼기 어렵다.

## 범위 제외

- 관리자 인증·인가 및 actor 모델의 구체적인 설계
- 감사 이력 조회 API와 관리자 화면
- 이력 보존 기간, 개인정보 삭제와 감사 보존 의무의 조정
- DB trigger, ORM 감사 도구, Outbox 기반 외부 감사 저장소 도입
