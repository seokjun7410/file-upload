# multipart 업로드 파일 용량을 100MB로 제한

## 문맥

파일 업로드 요청을 애플리케이션 서비스까지 전달한 뒤 크기를 검증하면
multipart 파싱과 파일 처리에 불필요한 메모리·디스크·네트워크 자원이 사용될 수
있다. 용량 제한이 없으면 단일 요청이 서버의 저장 공간이나 처리 자원을 과도하게
점유할 위험도 있다.

## 결정

- 업로드 파일 1개의 최대 크기는 100MB로 제한한다.
- multipart 전체 요청의 최대 크기는 110MB로 제한한다.
- 파일 1개 제한은 실제 파일 바이트 기준의 사용자-facing 업로드 한도이며,
  전체 요청 제한에는 multipart 경계와 요청 부가 정보에 필요한 여유를 포함한다.
- 용량 제한은 컨트롤러·서비스 로직보다 앞선 Spring Boot multipart 처리 단계에서
  적용한다.
- 제한을 초과한 요청은 파일 확장자·MIME·저장 검증을 실행하지 않고 거부한다.
- 용량 초과는 HTTP `413 Payload Too Large` 의미로 처리하며, 외부 응답에는 내부
  예외와 저장 경로를 노출하지 않는다.
- 확장자·MIME 검증은
  [ADR 0005](0005-limit-upload-to-known-non-executable-types.md)에 따라
  별도로 수행한다.
- 원본 파일명과 서버 저장 파일명의 매핑은
  [ADR 0006](0006-persist-upload-file-name-mapping.md)에 따라 별도로 관리한다.

## 설정 예시

```yaml
spring:
  servlet:
    multipart:
      max-file-size: 100MB
      max-request-size: 110MB
```

위 설정은 용량 정책을 애플리케이션의 multipart 경계에서 강제하기 위한 구현
수단이다. 프록시나 로드밸런서가 있는 환경에서는 동일한 정책이 앞단에서도
완화되지 않도록 별도로 확인한다.

## 고려한 대안

### 애플리케이션 서비스에서만 크기 검증

서비스에서 파일 크기를 확인하면 오류 응답을 세밀하게 제어하기 쉽지만, multipart
파싱 이후에 검증될 수 있어 서버 자원 보호가 늦어진다. 기본 제한 방식으로
채택하지 않는다.

### 인프라에서만 크기 제한

프록시에서 먼저 차단할 수 있지만 로컬·테스트 환경과 운영 환경의 정책이 달라질
수 있다. 인프라 제한은 보완적으로 적용하되 애플리케이션 제한을 함께 둔다.

### 제한을 적용하지 않음

구현은 단순하지만 자원 고갈과 저장 공간 고갈 위험을 허용하게 되므로 채택하지
않는다.

## 결과와 한계

- 100MB를 초과하는 단일 파일을 애플리케이션 업무 로직 전에 차단할 수 있다.
- multipart 전체 요청은 110MB를 초과할 수 없다.
- 용량 초과 오류를 프로젝트 공통 오류 응답으로 변환하는 처리가 필요하다.
- 이 결정은 단일 파일과 단일 multipart 요청의 크기만 제한한다.
- 사용자별 누적 한도, 일일 업로드 한도, 저장 공간 정리, 외부 오브젝트 스토리지는
  포함하지 않는다.

## 기존 결정과의 관계

이 ADR은 허용 파일 형식과 MIME 호환성을 결정한
[ADR 0005](0005-limit-upload-to-known-non-executable-types.md) 및 파일명 매핑과
저장 정책을 결정한 [ADR 0006](0006-persist-upload-file-name-mapping.md)을
보완한다. 용량 제한은 파일 내용과 메타데이터 정책과 독립적인 자원 보호 계층이다.
