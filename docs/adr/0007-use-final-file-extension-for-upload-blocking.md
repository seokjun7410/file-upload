# 업로드 차단은 파일명의 최종 확장자를 기준으로 한다

## 문맥

파일명에는 여러 개의 점이 포함될 수 있다. 예를 들어 `file.txt.exe`와
`file.exe.txt`는 서로 다른 의미로 사용될 수 있다.

파일명의 모든 점 이후 문자열을 차단 대상으로 해석하면 일반적인 문서 파일까지
과도하게 거부할 수 있다. 반대로 부분 문자열을 검색하면 실제 확장자가 아닌
문자열까지 차단하는 오탐이 발생한다.

## 결정

파일 업로드 차단 여부는 파일명의 가장 마지막 점 이후 문자열인 최종 확장자만
기준으로 판단한다.

정책에 등록된 확장자와 최종 확장자가 정규화 후 정확히 일치할 때 업로드를
차단한다. 중간 확장자와 부분 문자열은 자동으로 차단하지 않는다.

```text
차단 정책: exe

file.txt.exe  → 최종 확장자 exe → 차단
file.exe.txt  → 최종 확장자 txt → 허용
file.exe      → 최종 확장자 exe → 차단
file.exefoo   → 최종 확장자 exefoo → 허용
archive.tar.gz → 최종 확장자 gz → gz 정책에 따라 판단
```

## 정책 규칙

- 경로 구분자가 포함된 입력은 파일명 부분만 대상으로 한다.
- 확장자와 정책 값은 앞뒤 공백을 제거하고 소문자로 정규화한 뒤 비교한다.
- `contains`와 같은 부분 문자열 비교는 사용하지 않는다.
- 확장자 비교는 점 경계를 포함한 최종 suffix의 정확한 일치로 수행한다.
- `.bashrc`, `README`, `file.`처럼 최종 확장자를 추출할 수 없는 파일은 업로드를 거부한다.
- `file.exe.txt`는 `txt` 정책에 따라 판단하며, `exe`가 중간에 있다는 이유만으로 자동 거부하지 않는다.

## 고려한 대안

### 모든 확장자 세그먼트를 차단

`file.exe.txt`도 차단할 수 있지만, `report.final.v2.pdf`나 정상적인 복합
파일명까지 거부할 가능성이 높다. 최종 확장자 중심의 현재 서비스 목적에는
과도한 정책이므로 선택하지 않는다.

### 부분 문자열 검색

구현은 단순하지만 `file.exefoo`처럼 등록된 확장자를 포함하기만 하는 파일명을
차단할 수 있다. 확장자 경계를 표현하지 못하므로 선택하지 않는다.

### 복합 확장자 정책 등록

`exe.txt`를 별도 정책으로 등록해 정확히 차단하는 방식이다. 현재 요구사항은
최종 확장자 정책만 필요하므로 도입하지 않는다. 복합 확장자를 별도 정책으로
관리해야 하는 요구가 생기면 별도 ADR에서 정책과 API를 결정한다.

## 결과와 한계

- `file.txt.exe`처럼 실행 확장자가 최종 위치에 있는 파일을 일관되게 차단할 수 있다.
- `file.exe.txt` 같은 일반 문서 파일의 과도한 차단을 피할 수 있다.
- 고정·커스텀 정책의 의미와 업로드 판정 규칙이 단순해진다.
- 이 결정은 파일명의 최종 확장자에 대한 정책이며, 파일 내용의 실제 형식이나 악성 여부를 보장하지 않는다.
- 이중 확장자를 이용한 사용자 기만, MIME 위장, 악성코드 검사는 별도 보안 계층의 책임으로 둔다.

## 기존 결정과의 관계

이 ADR은 서버 생성 파일명과 정규화된 마지막 확장자 사용을 정한
[ADR 0003](0003-server-generated-file-storage-policy.md)의 업로드 차단 판정
기준을 명확히 한다. 확장자 정규화와 값 객체 생성은
[ADR 0004](0004-use-extension-name-value-object.md)의 결정을 따른다.

다중 점 파일명에 대한 위험과 대안은
[인터널 독스 2번](../../.internal-docs/file-upload-risk-analysis/02-case-double-extension.md)에
기록한다.
