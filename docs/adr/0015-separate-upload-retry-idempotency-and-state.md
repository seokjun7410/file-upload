# 파일 업로드의 requestId 기반 재시도·멱등성·상태 책임을 분리한다

## 배경

파일 업로드에서 네트워크 오류가 발생하면 FE는 같은 논리적 업로드를 다시 요청할 수 있다. 그러나 FE가 재시도한 횟수와 서버가 파일 저장을 시도한 횟수는 서로 다르다. 첫 요청이 파일 저장에 성공했지만 응답만 유실됐을 수도 있으므로, FE의 재시도 한도만으로 서버 파일을 실패 처리하거나 삭제하면 성공한 파일을 잃을 수 있다.

또한 서버가 멱등키를 받기만 하고 이전 처리 결과를 기억하지 않으면, 같은 키를 보내도 서버 생성 파일명이 매번 달라져 중복 파일이 생긴다. 현재 범위에서는 멱등키와 논리적 업로드 `requestId`를 같은 값으로 통합하되, FE 관찰 재시도 횟수와 서버 저장 상태는 별도로 관리한다.

## 결정

- FE는 하나의 **논리적 업로드 시도**를 시작할 때 불투명한 UUID v4 `requestId`를 한 번 생성하고 `Idempotency-Key` 헤더로 전송한다.
- 네트워크 오류·타임아웃으로 같은 요청을 재시도할 때는 기존 `requestId`를 유지한다. 사용자가 새 업로드를 시작하면 새로운 ID를 생성한다.
- `requestId`는 재시도 횟수나 인증 토큰이 아니라 동일 논리적 업로드를 식별하는 값이다. 현재 범위에서는 파일 SHA-256 지문을 추가하지 않고 ID의 1회 생성·재사용 계약에 의존한다.
- 서버는 `UploadFile`의 `requestId`와 처리 결과를 영속화하고, 동일 ID의 성공 결과가 있으면 파일을 새로 저장하지 않고 기존 결과를 반환한다. 동일 ID의 재사용은 별도 파일 지문 비교 없이 기존 상태·결과를 따른다.
- 서버는 중복 요청 관찰 횟수로 `Retry-After`의 capped exponential backoff와 jitter를 계산한다. FE의 자동 재시도 횟수·전체 대기 시간은 FE의 통신 정책으로 관리하며, FE 재시도 횟수는 서버 업로드 상태를 변경하는 조건이 아니다.
- 업로드 상태는 실제 서버 저장 생명주기만 표현한다. 현재 상태 모델의 `RECEIVING`, `COMPLETED`, `FAILED`를 따르며, FE가 재시도를 중단했다는 이유만으로 `RECEIVING`을 `FAILED`로 변경하지 않는다.
- 서버가 처리 중인 동일 `requestId` 요청을 발견하면 파일 저장을 다시 시작하지 않고 `409 IDEMPOTENCY_IN_PROGRESS`를 반환한다.
- 서버는 중복 요청 관찰 횟수에 따라 최소 1초·최대 30초의 capped exponential backoff와 jitter를 계산해 `Retry-After`로 제공한다. FE는 이 값을 따르되 최대 3회·전체 30초까지만 자동 재시도한다.
- 파일 정리는 서버가 저장 실패 또는 미완료를 확정한 임시·고아 파일을 대상으로 수행한다. FE 재시도 한도 초과만으로 최종 저장 파일을 삭제하지 않는다.
- `requestId`는 `Idempotency-Key`와 같은 값이며 논리적 업로드·응답·로그를 연결한다. 별도 `attemptId`는 추가하지 않는다.

## 처리 예시

```text
FE: requestId K1 생성
  → POST /files, Idempotency-Key: K1
  → 서버가 파일 저장 완료
  → 응답 유실

FE: K1으로 재시도
  → 서버가 K1의 COMPLETED 결과 확인
  → 새 파일을 만들지 않고 기존 성공 결과 반환
```

처리 중인 경우에는 다음처럼 서버 상태와 FE 재시도를 분리한다.

```text
FE: K1으로 재시도
  → 서버: K1 = RECEIVING
  → 파일 저장을 새로 시작하지 않음
  → 처리 중 응답
  → FE는 정해진 재시도 정책에 따라 K1을 다시 확인
```

## 상태와 책임

| 관심사 | 소유자 | 의미 |
|---|---|---|
| Retry-After 계산 | 서버 | 중복 요청 관찰 횟수에 따른 backoff와 jitter를 계산 |
| 자동 재시도 횟수·전체 대기 | FE | 서버 힌트를 따라 재요청하고 무한 재시도를 방지 |
| requestId/멱등키 | FE 생성·서버 검증 | 여러 HTTP 요청이 같은 논리적 업로드인지 식별 |
| 업로드 상태 | 서버 | 파일 저장이 접수·완료·실패했는지 표현 |
| 파일 정리 | 서버 운영 처리 | 확정된 실패·미완료 임시 파일과 고아 파일 정리 |

## 결과

- 네트워크 오류 후 FE가 같은 키로 재시도해도 서버가 이전 결과를 재사용할 수 있다.
- FE가 재시도를 포기해도 서버의 실제 저장 성공 여부가 임의로 바뀌지 않는다.
- 서버 상태와 통신 상태를 분리해 `UNKNOWN` 화면 상태와 서버 `RECEIVING`·`COMPLETED`·`FAILED`를 혼동하지 않는다.
- 멱등성 기록과 파일시스템은 하나의 ACID 트랜잭션이 아니므로, DB 선저장·임시 파일·원자적 확정·stale 복구는 [ADR 0014](0014-persist-upload-state-before-file-and-finalize-atomically.md)의 정책을 따른다.
- 키와 성공 결과에는 보존 기간과 정리 정책이 필요하다. 보존 기간이 지난 뒤 같은 키를 재사용하면 새 요청으로 처리될 수 있으므로, 이 기간은 FE의 재시도 가능 기간보다 길어야 한다.

## 고려하지 않은 것

- FE가 서버 `Retry-After`를 따르되 최대 3회·전체 30초로 자동 재시도를 제한하는 정책
- 처리 중 작업의 `202`·결과 조회 API 전환
- 별도 attemptId와 파일 SHA-256 요청 지문
- 비동기 업로드 작업과 결과 조회 API로의 전환
- 멱등키 기록의 저장소 종류와 보존 기간의 구체적인 숫자
- 파일 내용 검사·바이러스 검사·외부 오브젝트 스토리지
