# 원본 파일명과 서버 저장 파일명 매핑을 `UploadFile`로 영속화

파일명 충돌을 피하기 위해 실제 파일은 사용자가 전달한 파일명이 아니라 서버가 생성한 이름으로 저장한다. 그러나 원본 파일명을 저장하지 않으면 업로드 이후 사용자에게 원래 이름을 표시하거나, 원본 파일명과 저장 파일명을 연결해 다운로드할 수 없다. 요청 하나의 결과만 표현하는 `UploadedFile` record만으로는 이 매핑을 영속적으로 보존할 수 없다.

## 결정 초안

- 원본 파일명과 서버 저장 파일명의 영속적 매핑을 `UploadFile` 도메인 엔티티로 관리한다.
- `UploadFile`은 실제 파일 바이트를 보유하지 않고 파일 메타데이터만 보유한다.
- 저장 모델은 `p_upload_file` 테이블을 사용하며, 최소 필드는 다음과 같다.
  - `id`: 공통 엔티티 식별자
  - `original_filename`: 사용자에게 표시할 원본 파일명
  - `stored_filename`: 서버가 생성한 실제 저장 파일명
  - `created_at`, `updated_at`: 공통 생성·수정 시각
- `stored_filename`은 필수이며 unique 제약을 둔다. `original_filename`은 중복될 수 있으므로 unique 제약을 두지 않는다.
- 원본 파일명은 저장 경로가 아니라 표시용 메타데이터로만 취급한다. 경로 구분자가 포함된 입력은 basename만 사용하고, 원본 파일명을 파일 시스템 경로·저장 파일명·조회 식별자로 사용하지 않는다.
- 원본 파일명은 최대 255개의 Unicode code point까지 허용한다. 애플리케이션에서 입력을 검증하고 DB 컬럼도 최소 255자를 수용하도록 정의한다. Java `String.length()`의 UTF-16 code unit 수를 사용자에게 보이는 문자 수의 기준으로 사용하지 않는다.
- 빈 파일명, basename 추출 후 빈 이름, NUL을 포함한 제어 문자는 거부한다. 원본 파일명에 포함된 확장자는 서버의 확장자 추출·정규화 결과와 별도의 신뢰 경계로 취급한다.
- `stored_filename`은 UUID 등 서버 생성 식별자와 검증된 정규화 확장자로 구성한다. 원본 파일명의 길이·문자·경로 형식은 서버 저장 파일명에 영향을 주지 않는다.
- 업로드 흐름은 입력 및 정책 검증, 물리 파일 저장, `UploadFile` 메타데이터 저장 순서로 수행한다. 메타데이터 저장에 실패하면 이미 저장한 물리 파일을 보상 삭제하고 `FILE_UPLOAD_FAILED`로 처리한다.
- 차단되거나 입력 검증에 실패한 파일은 물리 파일과 `UploadFile` 레코드를 모두 생성하지 않는다.
- 현재 업로드 API의 `filename` 응답은 기존 계약과의 호환성을 위해 서버 저장 파일명을 의미한다. 원본 파일명을 응답하거나 다운로드 API에서 사용할 공개 식별자를 추가하는 것은 별도 API 결정으로 둔다.

## 고려한 대안

### 서버 저장 파일명만 반환하고 매핑을 저장하지 않음

현재 구현처럼 가장 단순하게 유지할 수 있지만, 업로드 이후 원본 파일명을 복원할 수 없다. 파일 목록·다운로드·업로드 이력 기능을 추가할 때 다시 저장 모델을 변경해야 한다.

### 원본 파일명과 저장 파일명을 별도 문자열이나 JSON으로 저장

초기 구현은 빠를 수 있지만, 파일별 조회·unique 보장·생성 시각 관리·삭제 연계를 표현하기 어렵다. 파일 메타데이터가 늘어날수록 구조화된 엔티티보다 유지보수성이 낮아진다.

### 파일 바이트까지 DB에 저장

메타데이터와 콘텐츠를 한 트랜잭션으로 관리할 수 있다는 장점은 있지만, 현재 로컬 파일 저장 정책과 맞지 않고 DB 크기·백업·응답 성능 부담이 커진다. `UploadFile`은 메타데이터만 저장하고 실제 콘텐츠는 `FileStorage`가 관리한다.

## 결과와 주의점

- 서버 생성 파일명과 원본 표시명을 분리하면서도 둘 사이의 관계를 DB에서 복원할 수 있다.
- 원본 파일명을 DB에 저장하므로 파일명 길이, 제어문자, 경로 입력에 대한 명시적인 입력 정책이 필요하다.
- 원본 파일명은 중복을 허용해야 한다. 같은 사용자가 `report.txt`를 여러 번 업로드해도 저장 파일명은 서로 달라야 한다.
- DB와 파일 시스템은 하나의 ACID 트랜잭션으로 묶이지 않으므로 보상 삭제가 필요하다. 저장소가 외부 오브젝트 스토리지나 비동기 처리로 확장되면 `PENDING`, `COMPLETED`, `FAILED` 상태와 재처리 정책을 별도로 검토한다.
- 파일 삭제·보존 기간·사용자 소유권·다운로드 권한은 이 결정에 포함하지 않는다. 해당 기능을 추가할 때 `UploadFile`의 생명주기와 접근 제어를 별도 결정한다.

## 기존 결정과의 관계

이 ADR은 서버 생성 파일명과 로컬 저장 위치를 정한 [ADR 0003](0003-server-generated-file-storage-policy.md)을 보완한다. ADR 0003에서 별도 정책으로 남겨 둔 원본 파일명 메타데이터를 `UploadFile` 엔티티와 길이 제한으로 구체화한다.
