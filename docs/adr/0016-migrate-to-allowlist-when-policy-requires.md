# 화이트리스트 전환은 명시적 조건과 단계적 마이그레이션으로 진행한다

## 배경

현재 파일 업로드 정책은 전역 denylist다. 등록되지 않은 확장자는 기본적으로
허용하고, 차단 대상으로 등록된 확장자만 막는다. 이 모델은 일반적인 파일 공유
서비스에서 새로운 확장자를 발견할 때마다 사전에 등록하지 않아도 되는 장점이
있다.

반면 규제 대상 서비스나 업무 포맷이 정해진 서비스에서는 알려진 형식만
허용하는 allowlist가 더 안전할 수 있다. 하지만 `blocked=false`인 현재 행을
그대로 허용목록으로 해석할 수는 없다. 현재 모델에서 `blocked=false`는
"이 행을 차단하지 않음"이라는 뜻이지, "이 확장자만 허용함"이라는 뜻이
아니기 때문이다.

사용자·조직별 정책을 지원할 때도 정책 행을 사용자마다 복제하기보다, 정책
집합을 만들고 사용자·조직과 정책 집합을 관계 테이블로 연결하는 방향이
적절하다. 관계 테이블은 적용 대상을 연결하는 역할이며, allowlist·denylist의
의미와 확장자 항목 자체를 대신 표현하지는 않는다.

## 결정

이 문서는 화이트리스트를 지금 즉시 적용하지 않고, 전환 판단 기준과 안전한
전환 절차를 먼저 결정하는 `proposed` ADR이다.

- 현재 프로젝트는 기존 전역 denylist를 유지한다.
- 화이트리스트 전환은 다음 조건을 모두 충족할 때만 검토한다.
  - 허용해야 하는 파일 형식의 범위가 업무적으로 충분히 알려져 있다.
  - 허용목록의 소유자와 변경 승인·감사 절차가 있다.
  - 기존 사용자가 올리던 파일 중 새 정책에서 거부될 파일을 식별할 수 있다.
  - 전환 전후 판정 결과를 비교할 관측 로그와 운영 대시보드가 있다.
  - 조직 또는 사용자 단위의 단계적 적용과 denylist 복귀가 가능하다.
- 사용자·조직별 정책은 정책 집합과 적용 대상의 관계로 모델링한다.
  - 정책 집합은 `mode`가 `DENYLIST`인지 `ALLOWLIST`인지 명시한다.
  - 정책 항목은 확장자와 허용·차단 의미를 표현한다.
  - 적용 관계는 `scope_type`, `scope_id`, `policy_set_id`를 연결한다.
  - 동일 대상에 여러 정책 집합이 연결될 수 있다면 우선순위와 상속 규칙을
    별도로 정의한다. 관계 테이블의 존재만으로 우선순위를 암묵적으로
    결정하지 않는다.
- 하나의 정책 집합 안에서는 denylist와 allowlist의 기본 의미를 섞지 않는다.
  정책 평가 결과는 `allowed`, 적용된 정책 집합, 범위, 거부 이유를 포함하는
  설명 가능한 decision으로 확장한다.
- 화이트리스트는 기존 파일에 소급 적용하지 않고 신규 업로드부터 적용한다.
  이미 완료된 파일을 차단하거나 재검사하는 요구는 파일 접근 정책 또는 보안
  사고 대응이라는 별도 결정으로 다룬다.

## 화이트리스트 전환이 적합한 시점

다음과 같은 경우에는 화이트리스트 전환의 이익이 크다.

- 의료·금융·공공 등 허용 파일 형식이 제한되고 감사가 필요한 환경
- 사내 업무 시스템처럼 문서·이미지·스프레드시트 등 입력 포맷이 정해진 환경
- 새로운 확장자를 허용하는 것보다, 운영자가 허용 여부를 승인하는 것이
  안전한 환경
- 파일 분석·바이러스 검사·다운로드 정책과 함께 허용 형식을 통제할 수 있는
  환경

다음과 같은 경우에는 전환을 늦추는 것이 좋다.

- 사용자가 다양한 파일 형식을 올리고, 사전에 업무 포맷을 정하기 어려운 경우
- 허용목록을 관리할 담당자나 변경 절차가 없는 경우
- 기존 업로드 데이터와 사용 패턴을 파악하지 못한 경우
- 신규 형식이 조용히 차단되어도 빠르게 발견·복구할 운영 수단이 없는 경우

## 전환 절차

### 1. 정책 의미와 우선순위 확정

스키마나 API를 먼저 바꾸지 않고 다음 정책을 확정한다.

- GLOBAL, ORGANIZATION, USER 중 어느 범위가 우선하는가
- 전역에서 강제 차단한 확장자를 조직·사용자가 허용할 수 있는가
- 조직 정책이 없는 사용자의 기본 모드는 무엇인가
- allowlist에 없는 확장자의 오류 코드와 사용자 안내는 무엇인가
- 기존 완료 파일을 계속 제공할 것인가

특히 전역 강제 차단을 하위 범위가 해제할 수 있는지는 보안 불변식으로 ADR에
명시해야 한다.

### 2. 허용목록을 별도로 큐레이션

기존 denylist에서 `blocked=false`인 행만 복사해 allowlist를 만들지 않는다.
등록되지 않은 확장자까지 허용되던 과거의 기본 동작이 포함되어 있기 때문이다.

- 공식적으로 허용할 확장자와 MIME·파일 형식을 선정한다.
- 각 항목의 업무 목적, 담당자, 승인 시각을 기록한다.
- 실행 파일·이중 확장자·위험 MIME처럼 확장자만으로 판단할 수 없는 위험은
  업로드 내용 검사 정책과 함께 검토한다.

### 3. Shadow 평가

실제 차단 동작은 기존 denylist로 유지하면서, 같은 업로드 요청을 새
allowlist로도 평가한다. 두 결과가 다른 요청을 기록해 다음을 확인한다.

- 정상 사용자가 새 정책 때문에 거부되는 비율
- 조직·사용자별 예외가 필요한 확장자
- 허용목록에 빠진 업무 필수 형식
- 현재 정책이 허용하지만 보안 검토가 필요한 형식

Shadow 결과가 안정되기 전에는 전환하지 않는다.

### 4. 단계적 적용과 안내

전체 사용자를 한 번에 전환하지 않고, 내부 사용자나 일부 조직부터 적용한다.
관리자 화면에는 확장자별로 "현재 정책에서는 허용되지만 전환 후 거부됨"과 같은
변경 예고를 보여줄 수 있어야 한다. 전환 전에 API 오류 코드, FE 안내 문구,
지원 문의 기준을 준비한다.

### 5. 신규 업로드에만 적용

전환 시점 이후의 신규 업로드부터 allowlist를 적용한다. 기존 완료 파일까지
자동으로 차단하면 정책 전환과 파일 접근 정책이 결합되어 사용자 영향과
복구 범위가 커진다. 기존 파일을 재평가해야 한다면 별도의 검사 결과·보존·복구
정책을 먼저 결정한다.

### 6. 모니터링과 복귀

전환 후에는 거부율, 오류 코드, 조직별 예외 요청, 관리자 정책 변경 이력,
업로드 성공률을 확인한다. 업무 중단이나 오탐이 확인되면 정책 집합의 mode를
기존 denylist로 되돌릴 수 있어야 하며, 전환 중 생성된 정책 항목과 이력은
삭제하지 않고 원인을 추적할 수 있게 보존한다.

## 데이터 모델 방향

향후 모델의 개념적 관계는 다음과 같다.

```text
PolicySet
  ├─ mode: DENYLIST | ALLOWLIST
  ├─ version
  └─ PolicyEntry(extension, effect)

PolicyAssignment(scope_type, scope_id, policy_set_id, priority)
```

`PolicyAssignment`는 사용자·조직·전역과 정책 집합을 연결한다. 실제 구현에서는
정책 집합의 소유 범위, 상속, 유효 기간, 변경 주체, 동일 확장자 중복 제약을
함께 설계해야 한다. 이 ADR은 구체적인 테이블명·컬럼 타입·API 경로를
확정하지 않는다.

## 고려한 대안

### 즉시 전역 allowlist로 전환

모델과 운영 규칙을 빠르게 단순화할 수 있다. 그러나 기존에 정상적으로
허용되던 미등록 확장자가 한 번에 차단되고, `blocked=false` 데이터를 잘못
이전할 가능성이 높아 선택하지 않는다.

### denylist와 allowlist를 요청별로 동시에 평가

보안 예외와 신규 형식 허용을 유연하게 조합할 수 있다. 하지만 정책 결과가
어떤 규칙으로 결정됐는지 설명하기 어려워지고, 우선순위·상속·예외 조합의
테스트가 크게 늘어난다. 정책 집합 단위로 mode를 명시하는 방향을 우선한다.

### 조직·사용자마다 정책 행을 복제

조회는 단순해 보이지만 전역 정책 변경을 모든 대상에 복제해야 하고, 사용자 수가
늘수록 데이터와 변경 작업이 증가한다. 정책 집합과 적용 관계를 분리하는
방향보다 상속·override를 관리하기 어렵다.

## 결과와 한계

- 현재 사용자의 동작을 유지하면서 화이트리스트 전환을 준비할 수 있다.
- 허용목록을 명시적으로 관리해야 하므로 보안은 강화되지만, 신규 정상 형식이
  누락되면 업로드가 거부될 수 있다.
- 정책 집합·항목·적용 관계 조회가 필요해 현재 전역 단일 조회보다 복잡해진다.
- 정책 변경 이력과 설명 가능한 decision이 있어야 운영자가 차단 원인을
  확인할 수 있다.
- 전환 기준의 구체적인 수치, 예를 들어 Shadow 기간이나 허용 실패율은 제품·운영
  데이터 확인 후 정한다.

## 결정 전 질문

- 우리 서비스는 규제·보안상 미등록 확장자를 기본 허용하면 안 되는가?
- GLOBAL 강제 차단을 하위 scope가 해제할 수 있는가?
- 정책 집합이 없는 사용자에게 적용할 기본 mode는 무엇인가?
- 기존 완료 파일을 allowlist로 재평가해야 하는가?
- 허용목록의 소유자와 승인자는 누구인가?
- Shadow 평가에서 허용할 최대 오탐·거부율을 얼마로 볼 것인가?
