# 업로드 저장 루트를 설정으로 외부화한다

## 문맥

[ADR 0003](0003-server-generated-file-storage-policy.md)은 허용된 파일을
프로젝트의 `./uploads`에 저장하고 서버 생성 파일명을 사용하도록 결정했다.
그러나 저장 루트가 코드에 고정되면 개발·테스트·운영 환경별 저장 위치를
변경하기 어렵고, 배포 환경의 디스크 구성과 애플리케이션 코드가 불필요하게
강하게 결합된다.

원본 파일명과 실제 저장 파일명을 분리하는 [ADR 0006](0006-persist-upload-file-name-mapping.md)의
구조를 유지하면서, 물리 파일이 저장되는 루트만 환경 설정으로 바꿀 수 있어야
한다.

## 결정

- 업로드 물리 파일의 저장 루트는 애플리케이션 설정으로 외부화한다.
- 설정 키는 `file.upload.storage-path`를 사용한다.
- 기본 저장 경로는 기존 정책과의 호환성을 위해 `./uploads`로 둔다.
- 저장 루트 설정은 서버 운영자가 관리하며, HTTP 요청이나 원본 파일명으로
  저장 경로를 결정하지 않는다.
- 실제 저장 파일명은 저장 루트와 독립적으로 서버가 생성한 이름을 사용한다.
- 저장 루트 아래의 파일명·하위 경로 조합은 애플리케이션이 관리하며, 원본
  파일명은 물리 저장 경로에 사용하지 않는다.
- 설정된 저장 루트에 접근할 수 없거나 파일을 저장할 수 없는 경우에는
  [ADR 0003](0003-server-generated-file-storage-policy.md)의
  `FILE_UPLOAD_FAILED` 오류 정책을 따른다.

### 설정 예시

```yaml
file:
  upload:
    storage-path: ./uploads
```

환경별 설정은 같은 키의 값을 바꾸어 적용할 수 있다. 예를 들어 테스트는
격리된 임시 디렉터리를, 운영은 별도 마운트된 파일 시스템 경로를 사용할 수
있다.

## 고려한 대안

### 저장 경로를 코드에 고정

구현은 단순하지만 환경별 저장 위치를 바꾸려면 코드를 변경해야 하고, 테스트가
실제 프로젝트 저장 디렉터리와 격리되기 어렵다. 기존 기본값은 유지하되
설정 변경을 지원하기 위해 선택하지 않는다.

### HTTP 요청에서 저장 경로를 받음

호출자가 저장 위치를 선택할 수 있지만 경로 조작, 권한 경계 우회, 운영 환경
노출 위험이 생긴다. 저장 경로는 서버 설정의 책임으로 제한한다.

### 시스템 임시 디렉터리만 사용

실행 환경 간 충돌을 줄일 수 있지만 파일 보존과 운영 중 조회가 불안정하고,
서비스 재시작·정리 작업에 따라 업로드 파일이 사라질 수 있다. 기본 저장소로
채택하지 않는다.

## 결과와 한계

- 환경별 저장 위치를 코드 변경 없이 지정할 수 있다.
- 테스트에서 저장 루트를 별도로 지정해 실제 업로드 파일과 테스트 파일을
  격리할 수 있다.
- 운영 환경은 설정된 경로의 존재 여부, 쓰기 권한, 디스크 용량과 백업을
  별도로 관리해야 한다.
- 저장 루트를 변경해도 기존 파일을 자동으로 이동하거나 메타데이터를
  마이그레이션하지 않는다. 기존 파일을 이동해야 하는 경우 파일 이동과
  설정 전환 절차를 별도로 마련해야 한다.
- 이 ADR은 로컬 파일 저장소의 루트 설정만 다룬다. S3·MinIO 같은 외부
  오브젝트 스토리지 도입, 파일 보존 기간, 삭제·백업 정책은 포함하지 않는다.

## 기존 결정과의 관계

이 ADR은 [ADR 0003](0003-server-generated-file-storage-policy.md)의 서버 생성
파일명·로컬 저장 정책을 변경하지 않고 저장 루트의 관리 방식을 구체화한다.
원본 파일명과 서버 저장 파일명의 매핑은
[ADR 0006](0006-persist-upload-file-name-mapping.md)의 책임으로 유지한다.
