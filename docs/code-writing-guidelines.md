# 코드 작성·리팩터링 규칙

## 목적과 적용 범위

이 문서는 파일 업로드 정책 프로젝트에서 코드를 작성하고 리팩터링할 때 따르는 구체적인 기준이다. `AGENTS.md`가 작업 범위, 문서 인덱스, 브랜치·커밋·검증 절차를 관리한다면, 이 문서는 클래스·메서드·패키지·테스트를 어떤 수준으로 설계하고 표현할지를 관리한다.

이번 세션의 기준은 두 종류로 나눈다.

- **사용자 판단으로 확정된 규칙**: 값 객체를 실제 도메인 경계에 사용한다, 낯선 Lombok 확장 기능을 쓰지 않는다, 필요하지 않은 추상화·flush·트랜잭션을 추가하지 않는다, 의존성은 주입한다, 패키지 이동은 move로 처리한다.
- **현재 코드에서 확인한 관례**: 명시적인 생성자와 도메인 행위, 기능 기준 패키지, 작은 concrete 모듈, 도메인별 예외 handler, 테스트 책임 분리. 새 요구사항과 충돌하면 요구사항을 우선하고 이 문서의 관례를 갱신한다.

## 1. 기본 방향

- 프로그래밍 초보자도 흐름을 따라갈 수 있도록 평범하고 명시적인 Java를 우선한다.
- 짧은 코드보다 책임과 동작이 한눈에 보이는 코드를 우선한다. 긴 함수형 체인, 숨은 생성 메서드, 과도한 다형성은 사용하지 않는다.
- 책임은 분리하되 클래스 수를 늘리는 것 자체를 목표로 삼지 않는다. 별도 테스트가 필요한 독립 책임이거나 변경 이유가 다를 때만 모듈을 분리한다.
- 한 구현만 있는 상황에서는 구체 클래스를 먼저 사용한다. 두 번째 구현, 교체 가능한 외부 연동, 명확한 테스트 대역 경계가 생길 때만 interface를 도입한다.
- 변경 범위는 요청된 동작과 그 동작을 안전하게 유지하는 테스트·문서로 제한한다. 관련 없어 보이는 구조 개선은 먼저 판단을 기록하고 승인받는다.

## 2. 패키지와 이동

### 2.1 기능 중심 패키지

파일 업로드 기능의 코드는 `com.example.demo.file` 아래에서 기능 경계를 기준으로 나눈다.

- `controller`: HTTP 요청 해석과 응답 변환
- `controller.dto.req`, `controller.dto.res`: API 입력·출력 모양
- `domain`: 정책 유형, 카탈로그, 정규화·검증 규칙
- `domain.entity`: JPA 엔티티
- `domain.entity.vo`: 엔티티가 사용하는 값 객체
- `repository`: 영속성 조회·저장 인터페이스
- `service`: 기능의 외부 계약과 저장·파일 저장 포트
- `service.impl`: 서비스 계약의 조정 로직과 구체 구현
- `exception`: 파일 업로드 기능에 특화된 실패 의미
- `exception.handler`: 기능별 예외를 REST 응답으로 변환
- `common`: 여러 기능에서 공유하는 공통 엔티티·REST 요청 오류·오류 응답

새 타입을 추가하기 전에는 가장 가까운 기존 책임을 확인한다. 패키지 경계가 바뀌면 `AGENTS.md`의 패키지 인덱스도 함께 갱신한다.

### 2.2 패키지 이동

패키지 이동은 삭제 후 새 파일 생성으로 처리하지 않는다. Git이 이동으로 추적할 수 있도록 `git mv` 또는 IDE의 move refactoring을 사용하고, 이동 전후의 내용 변경은 별도 목적의 변경으로 구분한다.

## 3. 도메인 모델과 값 객체

### 3.1 도메인 언어를 타입과 행위로 표현

- 정책 유형 비교가 서비스에 반복되면 엔티티에 의미 있는 행위를 만든다. 예를 들어 `policy.getPolicyType() == PolicyType.CUSTOM` 대신 `policy.isCustom()`을 사용한다.
- 정책의 판단 규칙은 엔티티·도메인 모듈에 둔다. 서비스는 저장소 조회, quota 잠금, 예외 전달, 여러 협력 객체의 순서를 조정한다.
- 단순 getter 조합으로 정책을 재현하지 말고 `isBlockedForUpload()`, `changeBlocked(boolean)`처럼 호출자가 결과의 의미를 이해할 수 있는 이름을 사용한다.
- enum은 상태나 유형 자체를 표현하고, enum을 여러 곳에서 조합해 정책을 재구현하지 않는다.

### 3.2 값 객체는 끝까지 전달

`ExtensionName`처럼 형식·정규화·동등성이 하나의 개념에 속하면 값 객체로 만든다.

- 값 객체 생성 시 정규화와 기본 형식 검증을 통과시켜 유효한 상태만 만든다.
- 값 객체는 불변으로 사용하고 setter를 만들지 않는다. 값 비교는 값 자체를 기준으로 한다.
- 서비스·도메인·저장소·파일 저장 포트는 가능한 한 `ExtensionName`을 주고받는다. 원시 `String`으로 되돌리는 변환은 HTTP, 파일명, DB 컬럼처럼 표현 형식이 필요한 경계에서만 한다.
- 정규화와 검증을 각 API·서비스·파일 처리 모듈에서 반복하지 않는다. 표기만 바꾸는 `ExtensionNormalizer`, 형식을 판단하는 `ExtensionValidator`, 유효한 상태를 보장하는 `ExtensionName`의 책임을 섞지 않는다.
- 값 객체의 변환 실패를 API나 파일 업로드 기능이 의미 있는 기능별 예외로 바꿔야 한다면 그 경계에서 변환한다. 도메인 내부까지 REST 예외를 끌어들이지 않는다.

### 3.3 JPA 매핑

- 엔티티의 JPA 기본 생성자는 명시적으로 남긴다. 도메인 불변식을 포함한 생성자와 정적 팩터리도 Lombok으로 숨기지 않는다.
- 값 객체는 필요하면 `@Embeddable`로 매핑해 도메인 타입을 유지한다. 기존 컬럼명을 유지해야 할 때는 `@AttributeOverride`로 매핑 의도를 직접 드러낸다.
- 엔티티 생성은 `fixed(...)`, `custom(...)`처럼 정책 의미가 드러나는 정적 팩터리를 사용한다.
- 엔티티 상태 변경은 setter 대신 도메인 행위 메서드로 제한한다.

## 4. 계층별 책임

### 4.1 Controller

- 컨트롤러는 요청 문자열을 도메인 타입으로 변환하고 서비스에 전달한다. 도메인 규칙을 다시 구현하지 않는다.
- 한 컨트롤러에서만 쓰는 얇은 입력 변환은 private 메서드로 둔다. 공개 클래스가 되면서 얻는 재사용성이 없으면 별도 parser 모듈을 만들지 않는다.
- DTO는 API 모양을 표현한다. 엔티티와의 변환은 `from(...)`처럼 호출 목적이 분명한 메서드로 둔다.
- 도메인·기능 예외는 해당 기능의 `exception.handler`에서 응답으로 바꾼다. `common`에는 모든 REST API에 공통인 요청 형식 오류만 둔다.

### 4.2 Service와 Repository

- 서비스는 여러 저장소·도메인 객체·파일 저장 포트의 순서를 조정한다. 조회 조건과 정렬처럼 저장소가 자연스럽게 책임질 수 있는 것은 repository 메서드에 표현한다.
- fixed와 custom처럼 결과 순서 자체가 계약이면 각각 정렬된 조회를 수행한 뒤 요구된 순서로 합친다. 서비스에서 전체 목록을 다시 정렬하는 중복 로직은 만들지 않는다.
- 단건 읽기에서 영속성 컨텍스트가 필요하지 않으면 불필요한 `@Transactional(readOnly = true)`를 붙이지 않는다. 여러 조회의 일관성이나 지연 로딩처럼 근거가 있을 때만 읽기 트랜잭션을 사용한다.
- 쓰기 트랜잭션에서는 관리 엔티티 변경을 dirty checking에 맡긴다. `saveAndFlush()`나 명시적 `flush()`는 커밋 전에 제약조건·후속 조회·외부 부작용이 반드시 발생해야 하는 경우에만 사용하고, 그 필요를 테스트로 설명한다.
- 동시성 요구가 있는 등록은 서비스의 사전 검사만 믿지 않는다. quota 행 잠금과 DB unique 제약처럼 저장소 수준의 보호를 함께 사용하고, 동시성 테스트로 계약을 고정한다.

### 4.3 예외

- 예외 이름은 호출자가 무엇을 할 수 없는지 드러내야 한다. 일반 `IllegalArgumentException`을 REST 응답까지 노출하지 않고, API·파일 업로드 같은 기능 경계에서 의미 있는 커스텀 예외로 변환한다.
- `EntityNotFoundException`처럼 도메인 전역에서 공통으로 쓸 수 있는 예외는 공통 타입으로 두고, 사용처가 도메인 이름을 문자열로 전달해 메시지를 만든다.
- 기능에만 의미가 있는 예외와 응답 매핑은 기능 패키지에 둔다. 공용 handler가 도메인별 예외를 모두 알게 만들지 않는다.

## 5. Lombok과 Java 표현

- 반복되는 생성자·getter·값 비교에는 익숙한 Lombok만 사용한다. 현재 기준은 `@RequiredArgsConstructor`, `@Getter`, `@NoArgsConstructor`, `@EqualsAndHashCode`다.
- `@Accessors(fluent = true)`, `@UtilityClass`처럼 메서드 이름이나 클래스 생성 방식을 숨기는 낯선 확장 기능은 사용하지 않는다.
- Lombok으로 JPA 기본 생성자, 도메인 검증·불변식 생성자, 명시적인 도메인 행위를 감추지 않는다.
- Lombok 적용 여부는 줄 수가 아니라 코드 독자가 실제 생성자·메서드·동작을 추적할 수 있는지를 기준으로 결정한다.
- `Optional.map`은 값을 변환하거나 조건 결과처럼 새로운 의미를 만들 때 사용한다. 단순 부수 효과를 위해 사용하지 않으며, 부수 효과에는 `ifPresent` 또는 명시적인 흐름을 사용한다. 조건 판정은 `map(...).orElse(false)`가 실제 반환 의미를 분명히 할 때만 사용한다.
- private 메서드도 이름만으로 책임과 반환 의미가 드러나도록 작성한다. 공개 타입·메서드와 private 메서드에는 필요한 Javadoc을 작성하고, 자명한 record accessor만 생략한다.

## 6. 테스트 작성 규칙

- 행동을 먼저 정의하고, 한글 `@DisplayName`으로 기대 결과를 고정한 뒤 red → green → refactor 순서로 진행한다.
- 도메인 규칙은 순수 도메인 테스트를 우선한다. JPA 매핑은 JPA 테스트로, HTTP 계약은 MockMvc·통합 테스트로 검증한다.
- 파일명 추출처럼 독립 책임이 생기면 해당 모듈을 직접 테스트하고, 업로드 서비스 테스트는 정책 판정·저장 호출 같은 orchestration에 집중한다.
- 테스트는 private 구현이 아니라 호출자가 관찰하는 결과·예외·협력 객체의 계약을 검증한다.
- 목록의 개수와 전체 순서는 요구사항 계약을 소유한 가장 가까운 테스트 한 곳에서만 고정한다. 그 외 테스트는 의미 있는 확장자·상태·필드로 항목을 찾는다.
- 정규화, 빈 입력, 경계 길이, 잘못된 확장자, 중복, quota 초과, 동시성처럼 실패 가능성이 있는 경계를 우선 테스트한다.
- 테스트 보조 메서드도 흐름이 복잡해지면 Javadoc을 작성하고, 테스트만 통과시키기 위한 과도한 fixture·mock을 만들지 않는다.

## 7. 리팩터링 점검 순서

1. 현재 요구사항·API 계약·기존 테스트를 확인하고, 변경하지 않아야 할 동작을 적는다.
2. `rg`로 중복 정규화·검증·enum 비교·예외 매핑·직접 생성·불필요한 `flush`와 트랜잭션을 찾는다.
3. 타입과 책임의 경계를 먼저 정한다. 값 객체로 전환할 때는 일부 메서드만 바꾸지 말고 서비스·저장소·저장 포트까지 흐름을 확인한다.
4. 새 공개 책임이면 테스트로 입력·반환·실패 계약을 먼저 고정한다. 단순 private 보조 로직은 공개 모듈로 승격할 충분한 책임과 테스트 가치가 있는지 확인한다.
5. 가장 작은 구현으로 동작을 유지하고, 중복과 과한 추상화를 제거한다.
6. 패키지 이동은 move로 처리하고, 문서 인덱스·Javadoc·관련 주석을 실제 구조와 맞춘다.
7. 대상 테스트, `./gradlew test`, `git diff --check`를 실행하고, 실패 원인과 수정 결과를 `PROMPT_LOG.md`에 남긴다.

## 8. 만들지 않을 것

- 한 구현만 있는 곳의 interface·adapter·factory
- 한 컨트롤러에서만 쓰는 얇은 parser 클래스
- 즉시 반영 근거가 없는 `saveAndFlush()`와 명분 없는 읽기 트랜잭션
- 컨트롤러·서비스마다 반복하는 정규화·유효성 검증
- enum 비교와 getter 조합으로 재현한 도메인 정책
- 코드 흐름을 숨기는 낯선 Lombok 확장 기능과 과도한 함수형 표현
- 요청 범위를 벗어난 패키지·API·스키마 변경
