# AI 프롬프트

> AI를 설계·구현·검증의 보조 수단으로 활용했다. AI의 제안을 바로 채택하지 않고, 요구사항·코드 검토·테스트·실제 화면 검증을 통해 범위와 정책을 결정했다.

- 전체 시간순 프롬프트·질문·검증 기록: [`PROMPT_LOG.md`](../PROMPT_LOG.md)
- 이 문서: 전체 기록 중 AI 활용 방식과 판단 과정을 보여주는 대표 사례 3건

## 사용한 skill / 도구

| skill / 도구 | 사용 작업 | 사용 이유 |
|---|---|---|
| `adr-predecision-review` | 정책 모델과 MIME 정책의 선택지 비교 | 구현 전에 대안·불변식·영향을 분리해 검토하기 위해 사용 |
| `tdd` | MIME 실패 처리와 정책 도메인 구현 | 기대 동작을 테스트로 먼저 고정하고 최소 구현을 만들기 위해 사용 |
| `diagnose` | MIME 분석 실패와 multipart 오류 재현 | 증상·원인·수정·회귀 검증을 분리하기 위해 사용 |
| `next-work-briefing` | 구현·브라우저 검증 범위 정리 | 목적·검증·제외 범위를 먼저 합의하기 위해 사용 |
| `backend-documentation` | 테스트 유지보수 기준과 검증 문서 정리 | 구현 방법이 아닌 계약과 검증 기준을 문서화하기 위해 사용 |
| `browser:control-in-app-browser`, `computer-use` | 정책 등록·오류·업로드 화면 확인 | 자동 테스트만으로 놓칠 수 있는 메시지와 포커스 흐름을 확인하기 위해 사용 |
| `skill-creator` | ADR 전 검토 방식 재사용 | 반복되는 설계 비교 절차를 일관된 skill로 정리하기 위해 사용 |

외부 plugin은 사용하지 않았다. 각 도구를 사용한 시점과 결과는 [`PROMPT_LOG.md`](../PROMPT_LOG.md)에 시간순으로 기록했다.

<details>
<summary><strong>사례 1. 구현 편의가 아닌 데이터 불변식으로 정책 모델 선택하기</strong></summary>

보완의 출발점: 기본 확장자와 사용자가 등록하는 확장자를 분리할지 하나의 정책으로 관리할지 결정해야 했다. 기존 코드를 적게 바꾸는 선택이 설계 판단에 섞이지 않게 하고 싶었다.

질문 1: fixed와 custom을 분리할지 하나의 엔티티와 유형으로 관리할지, 다른 선택지까지 예시와 장단점으로 비교하되 최종 결정은 내리지 마.

AI 답변:

- fixed/custom 분리 엔티티, 단일 정책 엔티티, 기본 카탈로그와 사용자 정책 분리 모델을 비교했다.
- 데이터 중복, 조회 방식, 유형별 행위, 향후 확장성을 기준으로 장단점을 정리했다.
- 추천 후보는 제시하되 최종 선택은 비워 둔 검토 문서를 작성했다.

행동: 검토 문서를 읽어보니 현재 구현 상태와 코드 변경 비용이 선택 근거에 섞여 있었다. 초안 설계에서 구현 편의가 데이터 의미보다 먼저 판단되는 것을 원하지 않아 비교 기준을 다시 요청했다.

질문 2: 현재 구현 상태와 코드 변경 비용은 선택 근거에서 빼고, 데이터 의미와 불변식만으로 다시 비교해줘.

AI 답변:

- 구현 편의와 변경 비용 문구를 제거했다.
- fixed와 custom이 모두 정규화된 확장자를 차단하는 정책이라는 공통 의미를 중심으로 다시 비교했다.
- 데이터 중복, 만들 수 있는 잘못된 상태, 필수값과 유형별 행위를 구분해 정리했다.

행동: fixed와 custom은 수정·삭제 가능 여부는 다르지만 같은 정책 개념이라고 판단했다. 중복과 필수값은 DB가 보장하고, 유형별 행위는 애플리케이션이 검증하도록 결정했다.

질문 3: fixed와 custom을 단일 `ExtensionPolicy`와 유형으로 관리하고, DB와 애플리케이션의 검증 책임을 나눈 ADR을 작성해줘.

AI 답변:

- 단일 엔티티와 `policy_type`을 사용하는 ADR 초안을 작성했다.
- 확장자 중복과 필수값은 DB 제약으로, 고정 카탈로그와 유형별 행위는 애플리케이션 검증으로 책임을 분리했다.
- 구현 전 검토 문서와 최종 ADR의 역할이 섞이지 않도록 정리했다.

행동: ADR 기준으로 구현한 뒤, 초기화·중복·200개 등록 한도·동시 등록·유형 제약을 테스트로 확인했다. AI의 첫 비교 문서는 그대로 쓰지 않았고, 판단 근거를 데이터 불변식 중심으로 바꾼 뒤 최종 결정을 기록했다.

내 최종 선택: 구현 편의가 아니라 정책의 공통 의미와 불가능한 상태를 기준으로 단일 `ExtensionPolicy` 모델을 선택했다.

- 관련 구현: `ExtensionPolicy` 단일 모델과 유형별 정책 검증

</details>

<details>
<summary><strong>사례 2. MIME 분석 실패를 “알 수 없는 형식”과 분리해 차단하기</strong></summary>

보완의 출발점: 확장자만으로 실행 파일 위장을 막기 어려워 파일 내용 기반 MIME 감지를 추가했다. 다만 형식을 알 수 없는 결과와 분석 자체가 실패한 결과를 어떻게 다룰지 정해지지 않았다.

질문 1: 파일 형식 감지 라이브러리를 비교하고, MIME 불일치와 실행 파일 검사의 범위를 정리해줘.

AI 답변:

- 파일 내용 기반 형식 감지에는 Apache Tika를 사용하고, 악성코드 검사는 별도 범위로 두는 방안을 제안했다.
- 처음에는 알려진 실행 MIME만 차단하고, 일반 텍스트와 형식을 특정하지 못한 파일은 허용하는 방향을 제안했다.
- MIME 감지만으로 악성 여부 전체를 판별할 수 없다는 한계를 함께 기록했다.

행동: 모든 허용 MIME을 관리하면 정상 파일까지 과하게 막을 수 있다고 판단했다. 현재 과제에서는 실행 파일 위장을 줄이는 범위로 좁히되, 검사 자체가 실패했을 때는 허용해도 되는지 구현을 확인했다.

질문 2: 확장자와 MIME이 다르다는 이유로 모두 차단하지 말고, 실제 실행 가능한 MIME만 차단해줘. 일반 텍스트는 허용해줘.

AI 답변:

- 파일 내용이 실행 MIME으로 감지될 때만 차단하도록 제안했다.
- `text/plain`과 형식을 특정하지 못한 결과는 기존 확장자 정책으로 처리하도록 정리했다.
- 실행 파일 헤더를 `.txt`로 위장한 테스트를 추가했다.

행동: 구현 후 코드를 읽으며 형식을 특정하지 못한 `UNKNOWN` 결과와 Tika 오류로 인한 분석 실패가 같은 분기로 처리되는 것을 발견했다. 보안 검사가 고장 난 경우까지 허용되는 것은 적절하지 않다고 판단했다.

질문 3: 분석은 성공했지만 형식을 모르는 경우와 분석 중 오류가 난 경우를 분리하고, 오류가 난 경우는 업로드를 중단해줘.

AI 답변:

- `UNKNOWN`과 `FAILED` 상태를 분리했다.
- 분석 실패는 파일 예약과 저장 전에 `FILE_TYPE_DETECTION_FAILED`로 차단하도록 제안했다.
- 외부 응답에는 내부 오류를 노출하지 않고, 원인은 서버 로그에만 남기도록 정리했다.

행동: “모르는 파일”은 정상적인 분석 결과일 수 있지만, “검사하지 못한 파일”은 보안 검사가 수행되지 않은 오류라는 점을 기준으로 판단했다. 실행 파일 위장·unknown·분석 실패를 각각 테스트해 결과를 확인했다.

내 최종 선택: MIME을 특정하지 못한 결과는 기존 정책으로 처리하고, MIME 분석 실패는 저장 전에 차단하도록 결정했다.

- 관련 구현: Apache Tika 기반 MIME 감지와 분석 실패 시 업로드 차단

</details>

<summary><strong>사례 3. 자동 테스트 통과 뒤 실제 사용자 흐름을 검증하기</strong></summary>

보완의 출발점: 확장자 정책은 20자까지, 최대 200개까지 등록할 수 있었지만 실제 화면에서 오류가 이해되는지와 실패 뒤 바로 재시도할 수 있는지는 확인하지 않았다.

질문 1: 20자·200개 정책 한도를 실제 화면에서 검증하고, 결과에 따라 UX 개선이 필요한지 판단할 수 있게 요구사항을 작성해줘.

AI 답변:

- 20자 등록 성공, 21자 등록 실패, 200개 목록 렌더링, 201번째 등록 실패를 브라우저 검증 항목으로 만들었다.
- 숫자를 미리 바꾸지 않고 실제 사용성을 확인한 뒤 유지·최소 개선·검색·페이징을 결정하도록 제안했다.
- 검증 계획은 장기 정책 ADR이 아닌 스프린트 요구사항으로 기록했다.

행동: 긴 입력과 많은 목록은 키보드·화면 확대·모바일 사용에도 영향을 준다고 판단했다. 완전한 접근성 구현으로 범위를 넓히지는 않되, 실제 사용 흐름을 확인할 최소 항목을 추가했다.

질문 2: 키보드 이동, 오류 안내, 모바일 화면을 이번 브라우저 검증 범위에 포함해줘. 확인하지 못한 접근성 항목은 완료로 표시하지 마.

AI 답변:

- 키보드 이동, 오류 안내, 포커스 복귀, 화면 확대와 모바일 가로 넘침을 확인 항목으로 정리했다.
- 완전한 WCAG 준수나 UI 프레임워크 교체는 이번 범위에서 제외했다.
- 자동화하기 어려운 항목은 수동 검증 대상으로 남기도록 했다.

행동: 격리된 DB와 임시 저장 경로에서 계획한 시나리오를 실제로 실행했다. 자동 테스트에서는 발견되지 않았지만, 서버의 영어 내부 메시지가 화면에 노출되고 삭제·업로드 실패 뒤 포커스가 `body`로 빠지는 문제를 발견했다.

질문 3: 발견된 문제만 API 계약을 바꾸지 않는 범위에서 수정하고, 정상·오류 흐름을 다시 검증해줘.

AI 답변:

- API 오류 코드는 유지하고 화면에서 코드별 한국어 메시지를 조립하도록 제안했다.
- 목록 변경 뒤에는 확장자 입력창으로, 업로드 종료 뒤에는 파일 입력창으로 포커스를 돌려주도록 수정안을 제시했다.
- 정책 한도, 업로드 오류, 작은 화면을 다시 검증하도록 정리했다.

행동: 실제 사용 흐름을 막는 두 문제만 최소 수정했다. VoiceOver와 실제 200% 확대처럼 확인하지 못한 항목은 성공으로 포장하지 않고 후속 수동 검증으로 남겼다.

내 최종 선택: 자동 테스트 통과를 완료 기준으로 삼지 않고, 실제 화면에서 메시지와 포커스 흐름까지 확인한 결과를 완료 기준으로 사용했다.

- 관련 검증: 정책 한도·업로드 오류·화면 포커스 흐름 확인

</details>

## 회고

AI는 빠르게 선택지를 넓히고 구현·테스트 초안을 만드는 데 유용했다. 반면 정책의 범위, 보안 실패의 의미, 완료 여부는 AI의 답변만으로 확정하지 않았다. 특히 코드의 상태 분기, 문서 diff, 테스트 결과, 실제 화면 흐름을 직접 확인하면서 제안을 수정하거나 보류했다.
