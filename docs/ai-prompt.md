# AI 프롬프트

> AI의 제안을 그대로 채택하지 않고, 부족한 조건을 다시 질문하고 범위를 조정한 뒤 검증 근거로 최종 선택을 정리한 기록이다.

## 1. UUID만으로 충분하다는 멱등성 답변을 서버 상태 관리로 보완하기

보완의 출발점: 파일 저장은 끝났지만 네트워크가 끊겨 응답을 받지 못하면, 사용자가 다시 업로드했을 때 같은 파일이 두 번 저장될 수 있었다.

질문 1: 네트워크 오류가 발생하면 화면에서 자동으로 다시 요청하고, 같은 멱등키를 유지하는 방식이 적절한지 검토해줘.

AI 답변:

- `adr-predecision-review`와 `diagnose` 관점으로 현재 업로드 API와 관련 ADR을 확인했다.
- 화면이 같은 키를 다시 보내는 것만으로는 중복 저장을 막을 수 없다고 설명했다.
- 서버가 키, 처리 상태, 성공 결과를 함께 기억해야 같은 요청의 결과를 다시 돌려줄 수 있다고 제안했다.
- 명확한 4xx 오류는 자동 재시도하지 않고 네트워크 오류에만 제한적으로 재시도하는 안을 제시했다.
- 아직 정하지 않은 보존 기간과 동시 요청 처리 방식은 코드로 만들지 않고 질문 문서에 남겼다.

행동: 멱등키를 쓴다는 방향만으로는 부족하다고 판단했다. 키를 어떤 값으로 만들고, 재시도 동안 어떻게 유지할지 다시 질문했다.

질문 2: 멱등키는 구체적으로 어떤 값으로 만들고, 파일명이나 사용자 정보도 키에 넣어야 해?

AI 답변:

- 파일명·사용자 ID·시간·파일 해시를 조합하면 개인정보와 정규화 문제가 생길 수 있다고 설명했다.
- 화면에서 논리적 업로드마다 UUID v4를 하나 만들고, 같은 업로드의 재시도에만 그 값을 유지하는 방식을 제안했다.
- 서버에서는 `요청 범위 + API 경로 + 키`를 식별자로 저장하고, 다른 요청 내용에 같은 키가 재사용되는 문제는 별도 지문으로 확인하는 안을 제시했다.
- 로그 추적용 requestId와 멱등키는 역할이 다르므로 일단 분리해서 설명했다.

행동: UUID 형식은 이해됐지만 “클라이언트 UUID 하나면 충분하다”는 결론으로 오해할 수 있다고 판단했다. 서버 측 보장 조건을 다시 물었다.

질문 3: 그러면 클라이언트가 만든 UUID 하나만 있으면 멱등성이 보장되는 거야?

AI 답변:

- UUID는 충돌 가능성이 낮은 키 형식일 뿐, 그 자체가 중복 처리를 막지는 않는다고 답했다.
- 서버가 키와 처리 결과를 저장하고, 같은 키의 요청을 다시 실행하지 않아야 멱등성이 성립한다고 정리했다.
- UUID v7의 정렬 특성은 멱등성 강도를 높이지 않으므로 현재 요구에는 UUID v4로 충분하다고 설명했다.
- 클라이언트 UUID만 추가하는 부분 구현은 완료된 멱등성으로 보지 말아야 한다고 기록했다.

행동: 같은 키의 첫 요청이 아직 처리 중일 때 두 번째 요청이 오면 영원히 기다리거나 파일이 중복될 가능성이 있다고 보고 처리 중 상태를 질문했다.

질문 4: 같은 키의 요청이 처리 중이면 예외만 반환해도 돼? 서버가 멈추면 그 상태가 계속 남지 않을까?

AI 답변:

- 처리 중 상태를 최종 실패가 아닌 중간 상태로 다뤄야 한다고 답했다.
- 중복 요청은 새 파일을 저장하지 않고 처리 중 응답과 재시도 안내를 반환하는 방안을 제시했다.
- 서버 중단 후 남은 상태를 복구하려면 lease, 작업 소유자, 시도 버전 같은 장치가 필요하다고 설명했다.
- 동기 API의 짧은 대기와 상태 조회 API를 둔 비동기 방식은 선택이 필요한 대안으로 남겼다.

행동: 화면의 재시도 횟수가 서버 상태와 파일 삭제에 영향을 줘도 되는지 의문이 생겼다. 세 번 실패하면 서버 파일을 실패 처리하고 삭제하는 안을 검토해달라고 요청했다.

질문 5: 화면이 세 번 재시도한 뒤 포기하면 업로드 상태를 실패로 바꾸고 파일을 삭제해도 될까?

AI 답변:

- 화면이 응답을 세 번 받지 못했다는 사실과 서버가 파일 저장을 세 번 실패했다는 사실은 다르다고 설명했다.
- 첫 요청은 성공했지만 응답만 사라졌을 수 있으므로 화면의 재시도 횟수로 최종 파일을 삭제하면 안 된다고 답했다.
- 화면의 관찰 횟수와 서버의 실제 저장 시도 횟수를 분리하고, 서버가 실패를 확정한 임시 파일만 정리하도록 제안했다.
- 화면은 결과를 알 수 없는 상태로 끝낼 수 있지만 서버의 성공·실패 상태는 실제 저장 결과만 표현해야 한다고 정리했다.

행동: 이 답변을 채택했다. 이어 파일 저장 제한 시간과 `Retry-After`를 같은 값으로 맞춰도 되는지 질문했다.

질문 6: 파일 저장 제한 시간을 넉넉하게 두고 그 값만큼 `Retry-After`를 주면 되는 거야?

AI 답변:

- 서버 작업의 최대 실행 시간, 다음 상태 확인까지 기다릴 시간, 화면이 기다릴 전체 시간은 서로 다른 값이라고 답했다.
- RFC 9110과 외부 멱등성 사례를 확인해 `Retry-After`는 짧은 재확인 간격으로 사용하고 저장 제한 시간과 동일하게 두지 않는 방향을 제안했다.
- 제한 시간이 지난 작업은 소유권과 lease를 확인해 실패 또는 재처리 가능 상태로 전환하고, 확정된 임시 파일만 정리하도록 정리했다.

행동: 세부 상태를 모두 구현하기보다 먼저 변하지 않을 원칙을 정하기로 했다. 재시도, 멱등키, 서버 저장 상태를 서로 독립적으로 관리하는 ADR과 파일 저장 순서를 요청했다.

질문 7: 재시도 횟수, 멱등키, 서버 상태를 분리하고 파일은 임시 경로에 저장한 뒤 확정하는 방향으로 정리해줘.

AI 답변:

- 재시도는 화면의 통신 전략, 멱등키는 같은 논리적 요청 식별, 업로드 상태는 실제 서버 저장 결과로 책임을 분리한 ADR을 작성했다.
- DB에 `RECEIVING` 상태를 먼저 저장하고, 같은 파일시스템의 임시 경로에 파일을 쓴 뒤 atomic move로 최종 파일을 확정하는 순서를 제안했다.
- 파일 저장이 완료되고 DB 상태가 `COMPLETED`로 커밋된 뒤에만 성공 응답을 반환하도록 정리했다.
- 파일 I/O 동안 DB 트랜잭션을 오래 유지하지 않고, 오래 남은 `RECEIVING` 복구는 별도 요구로 분리했다.

행동: 프로젝트에는 업로드 API가 하나뿐이므로 식별자를 둘로 유지하는 복잡성을 줄이기로 했다. 멱등키 UUID를 논리적 업로드 requestId로 통합해 구현하도록 요청했다.

질문 8: `Idempotency-Key` UUID를 업로드 requestId로 통합하고, 처리 중 응답과 결과 재사용까지 TDD로 구현해줘.

AI 답변:

- `tdd`로 헤더 검증, 상태 선저장, 임시 저장, atomic move, 완료·실패 결과 재사용, 처리 중 응답을 구현했다.
- 처리 중 요청에는 `409`와 서버가 계산한 `Retry-After`를 반환하도록 했다.
- 화면은 같은 requestId로 최대 3회, 전체 30초 범위에서 다시 요청하도록 변경했다.
- 별도 attemptId, SHA-256 지문, 비동기 작업 API는 현재 범위에 추가하지 않았다.
- controller·integration·domain·recovery 테스트와 전체 99개 테스트, JavaScript 문법 검사를 통과했다.

행동: 자동 테스트 결과를 확인하고 구현을 채택했다. 키 보존 기간과 브라우저 사용성 검증은 완료로 주장하지 않고 후속 작업으로 남겼다.

내 최종 선택: 최초의 “UUID를 붙여 재요청” 아이디어는 그대로 사용하지 않았다. 실패 상황을 작은 질문으로 나눈 뒤 서버 결과 저장과 상태 전이를 포함하는 구조로 수정해 사용했다.

## 2. 형식을 모르면 허용한다는 MIME 답변을 분석 실패 차단으로 보완하기

보완의 출발점: 파일 확장자는 쉽게 바꿀 수 있어 파일 내용으로 형식을 확인하려 했지만, 어디까지 차단해야 하는지와 분석 실패를 어떻게 처리할지가 정해지지 않았다.

질문 1: 파일 형식 감지 라이브러리를 비교하고, MIME 불일치와 실행 파일·악성코드 검사의 범위를 ADR로 정리해줘.

AI 답변:

- `adr-predecision-review`를 사용해 Apache Tika 공식 문서와 JDK MIME 감지 방식을 비교했다.
- `tika-core`는 파일 내용 기반 형식 감지에 사용하고, Parser나 악성코드 검사는 별도 범위로 두는 안을 제안했다.
- 처음에는 “알려진 비실행 파일 형식만 허용”하는 보수적인 정책을 추천했다.
- MIME 감지만으로 실행 가능성이나 악성 여부를 완전히 판단할 수 없다는 한계를 ADR에 남겼다.

행동: 모든 허용 형식을 관리하면 정상 텍스트 파일까지 과하게 막을 수 있다고 판단했다. 현재 과제에서는 실행 가능한 파일 위장만 줄이는 수준으로 범위를 좁혀 다시 요청했다.

질문 2: 확장자와 MIME이 다르다는 이유로 모두 차단하지 말고, 실제 실행 가능한 MIME만 막아줘. 일반 텍스트는 허용해줘.

AI 답변:

- `next-work-briefing`과 `tdd`로 실행 MIME 카탈로그와 Tika 감지기 구현 범위를 정리했다.
- 파일 내용이 실행 MIME으로 확인될 때만 `BLOCKED_EXECUTABLE_MIME`으로 거부하도록 구현했다.
- 실제 MZ 헤더를 가진 파일을 `.txt`로 위장한 테스트를 추가했다.
- `text/plain`, 형식을 특정하지 못한 결과, 감지 중 오류는 기존 확장자 정책으로 넘기도록 했다.
- 카탈로그·감지기·서비스·MockMvc·전체 테스트를 통과했다.

행동: 구현 후 코드를 다시 읽다가 형식을 특정하지 못한 결과와 Tika가 오류로 실패한 결과가 같은 `isUnknown()` 분기에 들어가는 것을 발견했다. 보안 검사가 고장 난 경우에도 업로드가 허용되는 것이 맞는지 다시 물었다.

질문 3: 분석은 성공했지만 형식을 모르는 경우와 `IOException`으로 분석에 실패한 경우를 분리하고, 실패한 경우는 업로드를 중단해줘.

AI 답변:

- OWASP File Upload Cheat Sheet와 현재 MIME 처리 코드를 대조했다.
- `UNKNOWN`과 `FAILED` 상태를 분리하고, `FAILED`는 예약과 파일 저장 전에 거부하는 정책을 제안했다.
- 외부 응답은 `FILE_TYPE_DETECTION_FAILED`로 고정하고 Tika 오류 원인은 내부 로그에만 남기도록 정리했다.
- `application/octet-stream`은 분석 성공 후 형식을 특정하지 못한 결과이므로 계속 허용했다.
- 새 예외가 없어 테스트 컴파일이 실패하는 Red 상태를 먼저 확인한 뒤 서비스·REST·FE 메시지를 구현했다.
- MIME·Tika·REST 테스트, 전체 Gradle 테스트, JavaScript 문법 검사를 통과했다.

행동: “모르는 파일”과 “검사하지 못한 파일”을 분리한 결과를 채택했다. MIME allowlist, 악성코드 검사, 파일 미리보기 보안은 현재 과제의 완료 항목으로 추가하지 않았다.

내 최종 선택: 최초에는 감지 실패도 허용했지만, 구현을 다시 검토해 보안 검사가 실패한 경우에는 저장하지 않는 방향으로 수정했다.

## 3. 커밋 복구 결과를 파일 경계와 독립 검증으로 다시 통제하기

보완의 출발점: 정책 REST API, 기존 코드 정리, 문서 변경이 한 이력에 섞여 각 변경의 귀속을 확인할 수 없었다.

질문 1: docs 브랜치에는 문서만, 기존 동작을 보존하는 정리는 코드 커밋만, REST API는 미커밋 상태로 분리해줘.

AI 답변:

- 미커밋 API를 보존하고 코드·문서 커밋을 다시 구성한 뒤 API 파일만 복원했다.
- `git show`, `git log --name-only`, 전체 테스트와 공백 검사로 결과를 확인했다고 보고했다.

행동: 복구 결과를 직접 검토하니 삭제됐어야 할 예제 파일이 남았고, 다음 결과에는 기존 스타일 변경이 API 작업 트리에 다시 섞여 있었다. 결과를 채택하지 않고 커밋별 허용 경로·삭제 경로·미커밋 경로를 먼저 확정했다.

질문 2: 확정한 파일 목록을 기준으로 다시 복구하고, 각 커밋이 독립적으로 컴파일·테스트되는지 확인해줘.

AI 답변:

- 코드 커밋에는 기존 기능과 필요한 삭제만, 문서 커밋에는 `AGENTS.md`, `PROMPT_LOG.md`, `docs/**`만 남겼다.
- REST API는 작업 트리에만 복원하고 커밋별 경로·삭제 상태·전체 테스트를 재검사했다.
- 후속 리뷰에서 발견한 필수 필드 누락은 `@NotNull`과 MockMvc 테스트로 수정해 `INVALID_REQUEST`와 `INVALID_EXTENSION`을 구분했다.

내 최종 선택: AI의 복구 보고를 그대로 믿지 않고 파일 목록, 삭제 상태, 독립 테스트를 완료 기준으로 삼았다. 그 기준으로 커밋 경계와 입력 검증을 다시 맞춘 결과만 채택했다.

## 4. 자동 테스트 완료 판단을 실제 사용자 흐름 검증으로 보완하기

보완의 출발점: 확장자 정책은 20자까지, 최대 200개까지 등록할 수 있었지만 실제 화면에서 긴 입력과 많은 목록, 오류 후 재시도가 가능한지는 확인하지 않았다.

질문 1: 20자·200개 정책 한도를 실제 화면에서 검증하고, 결과에 따라 UX 개선이나 정책 변경이 필요한지 판단할 수 있게 요구사항을 작성해줘.

AI 답변:

- `backend-documentation`으로 현재 20자 validator, 200개 quota, 전체 목록 API와 오류 계약을 확인했다.

- 숫자를 미리 바꾸지 않고 실제 사용성을 확인한 뒤 유지·최소 개선·검색·페이징을 결정하도록 정리했다.
- 검증 계획은 장기 결정인 ADR이 아니라 스프린트 요구사항으로 기록했다.

행동: 긴 입력과 많은 목록은 모바일·키보드·스크린리더 사용에도 영향을 준다고 판단했다. 완전한 접근성 구현으로 범위를 키우지 않으면서 최소 확인 항목을 추가하도록 요청했다.

질문 2: 키보드, 스크린리더, 200% 확대, 모바일 화면도 이번 브라우저 검증 범위에 포함해줘.

AI 답변:

- 키보드 이동, 오류 안내, 포커스 복귀, 스크린리더 상태 전달, 화면 확대와 모바일 가로 넘침을 확인 항목으로 추가했다.
- 완전한 WCAG 준수나 UI 프레임워크 교체는 범위에서 제외했다.

행동: 기능 구현이 끝난 뒤 격리된 DB와 임시 저장 경로에서 계획한 시나리오를 실제로 실행하고, 문제가 나오면 API를 바꾸지 않는 범위에서 수정하도록 요청했다.

질문 3: 20자·200개 한도와 업로드 오류를 실제 브라우저에서 검증하고, 발견된 문제만 최소 범위로 수정해줘.

AI 답변:

- 21자와 201번째 오류에서 서버의 영어 내부 메시지가 화면에 그대로 노출되는 문제를 발견했다.
- 삭제와 업로드 실패 뒤 포커스가 `body`로 빠져 키보드로 바로 재시도하기 어려운 문제를 발견했다.
- 서버 API와 오류 코드는 유지하고 화면에서 code별 한국어 메시지를 만들도록 수정했다.
- 목록 변경 뒤 확장자 입력창, 업로드 종료 뒤 파일 입력창으로 포커스를 돌려주도록 수정했다.
- 브라우저 캐시에 이전 JavaScript가 남지 않도록 정적 파일 URL에 버전 값을 붙였다.

질문 4: 기본 업로드, 정책 한도, 같은 requestId 동시 요청, 반응형과 접근성 검증을 한 세션에서 다시 실행해줘.

- 실제 실행 MIME으로 감지되는 MZ 헤더 fixture로 보안 시나리오를 다시 확인했다.
- 같은 requestId 12개를 동시에 보내 성공 1건, 처리 중 응답, 최종 파일 1개를 확인했다.
- 320px와 640px에서 가로 넘침이 없음을 수치로 확인했다.
- 외부 Chrome이 사용자 조작 상태로 바뀌자 사용자 탭을 덮어쓰지 않고 자동화를 중단했다.
- VoiceOver, 실제 200% 확대, 브라우저에서의 409 화면 주입은 미확정으로 기록했다.

행동: 확인한 항목만 완료로 표시하고 자동화하지 못한 세 항목은 미완료로 남겼다.

내 최종 선택: 자동 테스트 통과를 완료 기준으로 삼지 않고 실제 화면에서 메시지와 포커스 문제를 찾아 수정했다. 확인하지 못한 접근성 결과는 성공으로 포장하지 않았다.

## 5. 단순 확장자 검사안을 실제 우회 사례와 요구 근거로 보완하기

보완의 출발점: 확장자 입력 문자 범위와 다중 점 파일명의 검사 기준을 정하는 과정에서, 기존 정책을 어디까지 바꿔야 하는지 판단이 여러 번 달라졌다.

질문 1: 커스텀 확장자는 특수문자를 제외하고 한글·영문·숫자만 허용하도록 ADR에 반영해줘.

AI 답변:

- 기존 값 객체 ADR에 한글·영문·숫자 허용 규칙을 추가했다.
- API 계약과 체크리스트에도 같은 규칙을 반영했다.
- 향후 `ExtensionValidator`에서 커스텀 입력과 업로드 확장자에 같은 검증을 적용하도록 제안했다.

행동: 기존 값 객체 ADR은 이미 구현이 끝난 결정인데 새로운 입력 정책을 덧붙이면 과거 결정과 후속 변경이 섞인다고 판단했다. 별도 ADR로 분리하도록 요청했다.

질문 2: 기존 ADR은 원래 내용으로 돌리고, 허용 문자 정책은 새로운 ADR로 분리해줘.

AI 답변:

- 기존 ADR에서 허용 문자 내용을 제거했다.
- 새 ADR 0010과 API 계약·체크리스트·문서 인덱스에 정책을 분리해 기록했다.
- 코드와 테스트는 아직 바꾸지 않고 후속 구현으로 남겼다.

행동: 이어 `file.txt.exe`와 `file.exe.txt`를 어떻게 판단할지 질문했다. 정상적인 다중 점 파일을 과하게 막지 않기 위해 마지막 확장자 기준을 우선 검토했다.

질문 3: 다중 점 파일은 마지막 확장자만 정확히 비교하는 정책으로 정리해줘.

AI 답변:

- 모든 구간 검사, 부분 문자열 검사, 마지막 확장자 exact match를 비교했다.
- `file.txt.exe`는 차단하고 `file.exe.txt`는 중간 `exe`만으로 차단하지 않는 정책을 ADR로 작성했다.
- 확장자 검사만으로 파일 내용과 악성 여부를 판단할 수 없다는 한계를 남겼다.

행동: 이후 스프린트 구현 순서를 검토하면서 한글·영문·숫자 제한이 현재 요구에 꼭 필요한지 다시 확인했다. 제한 대상이 전체 파일명이 아니라 마지막 확장자라는 점도 명확히 했다.

질문 4: ADR 0010의 필요성을 다시 검토하고, 요구 근거가 부족하면 이번 스프린트에서 빼줘.

AI 답변:

- 현재 코드와 문서에서 이미 빈 값, 20자, 점을 검증하고 있음을 확인했다.
- 한글·영문·숫자만 허용해야 할 제품 요구는 확인되지 않았다고 정리했다.
- ADR은 결정 기록으로 남기되 구현 순서에서는 제외하고 기존 동작을 유지했다.

행동: 불필요한 입력 제한은 보류했다. 이후 `test.exe.pdf`, `test.jsp.png`처럼 중간에 차단 확장자를 숨기는 실제 우회 사례가 제기되어 마지막 확장자 정책을 다시 바꾸기로 했다.

질문 5: 중간 확장자에 차단 대상이 있으면 업로드를 막되, 기존 오류 응답과 정상 복합 파일명은 유지해줘.

AI 답변:

- `next-work-briefing`, `tdd`, `backend-documentation`을 사용하고 OWASP·CWE 자료를 확인했다.
- 파일명의 모든 확장자 구간을 왼쪽부터 exact match로 비교하는 정책을 새 ADR로 작성했다.
- 여러 차단 구간이 있으면 첫 번째 구간만 기존 `context.extension`에 담아 API 구조를 바꾸지 않는 안을 제시했다.
- `extractAll`이 없어 테스트 컴파일이 실패하는 Red 상태를 확인한 뒤 전체 구간 추출과 서비스 판정을 구현했다.
- `test.exe.pdf`, 대소문자 변형은 차단하고 `test.exefoo.pdf` 같은 부분 문자열은 허용하는 테스트를 통과했다.
- 단위·서비스·HTTP 통합·전체 테스트와 공백 검사를 통과했다.

행동: 정상 파일 오탐과 기존 API 변경을 최소화한 점을 확인해 새 정책을 채택했다. 이전 마지막 확장자 ADR은 삭제하지 않고 대체된 결정으로 보존했다.

내 최종 선택: 처음 제안한 문자 제한은 구현하지 않았고, 마지막 확장자만 보던 정책은 실제 우회 사례를 근거로 모든 확장자 구간을 검사하도록 변경했다.

## 6. 과도한 용량·서버 세부 구현을 과제 범위와 안전한 오류 계약으로 보완하기

보완의 출발점: 서버 자원 보호를 위해 업로드 크기를 제한해야 했지만 초기 수치와 구현 설명이 과제 규모에 비해 컸고, multipart 오류에는 내부 정보가 섞일 가능성이 있었다.

질문 1: 서버 설정으로 업로드 용량을 제한하는 방안을 검토하고 100MB 기준 ADR을 만들어줘.

AI 답변:

- 파일 하나는 100MB, multipart 전체 요청은 부가 정보 여유를 포함해 110MB로 제한하는 ADR을 작성했다.
- 서비스 코드보다 앞선 multipart 파싱 단계에서 큰 요청을 차단하도록 제안했다.
- 초과 요청은 `413 Payload Too Large` 의미로 처리하고 실제 설정과 handler는 후속 구현으로 남겼다.

행동: 과제에서 100MB 파일을 받을 이유가 부족하다고 판단했다. 정상 경계 파일이 multipart 부가 정보 때문에 거부되지 않도록 파일과 요청 한도는 분리하되 수치를 낮추도록 요청했다.

질문 2: 파일은 10MB, 전체 요청은 12MB로 바꾸고 실제 설정과 413 응답을 구현해줘.

AI 답변:

- `tdd`로 설정값과 `FILE_SIZE_EXCEEDED` 413 응답을 구현했다.
- 처음에는 Tomcat이 거부된 본문을 처리하도록 `max-swallow-size` 설정과 실제 대용량 HTTP 통합 테스트까지 추가했다.
- 설정·MockMvc·내장 서버·전체 테스트를 통과했다고 보고했다.

행동: 과제 설명에 Tomcat 내부 옵션과 큰 파일 통합 테스트까지 포함하는 것은 핵심보다 구현 세부를 크게 만든다고 판단했다. 용량 정책을 설명하는 데 필요한 최소 구조만 남기도록 다시 요청했다.

질문 3: `max-swallow-size`와 과도한 대용량 통합 테스트를 제거하고, 10MB·12MB 설정과 413 변환만 남겨줘.

AI 답변:

- 용량 초과 예외는 공통 REST Advice가 처리하도록 단순화했다.
- 파일 업로드 전용 예외 handler는 도메인 예외만 담당하도록 범위를 복원했다.
- 설정 바인딩 테스트와 413 매핑 테스트만 유지했다.
- 관련 테스트와 전체 회귀 테스트를 통과했다.

행동: 이후 예외 handler 코드를 직접 보다가 `MultipartException.getMessage()`가 응답에 그대로 들어가 Spring·Tomcat 내부 문구나 임시 파일 경로를 노출할 수 있음을 발견했다. 해당 예외만 안전한 응답으로 바꾸도록 요청했다.

질문 4: multipart 내부 예외 메시지는 외부에 보내지 말고 고정된 `INVALID_FILE` 응답을 주고, 원인은 requestId와 함께 서버 로그에만 남겨줘.

AI 답변:

- `diagnose`로 내부 경로가 포함된 `MultipartException`을 재현하는 MockMvc 테스트를 추가했다.
- 수정 전 응답에 내부 경로가 나타나 테스트가 실패하는 Red 상태를 확인했다.
- 외부 메시지를 `잘못된 파일 요청입니다.`로 고정하고 예외 객체는 requestId와 함께 warn 로그로 남겼다.
- 다른 파일 업로드 예외의 메시지 계약은 바꾸지 않았다.
- 대상 테스트, controller 테스트, multipart 제한 통합 테스트, 전체 테스트와 공백 검사를 통과했다.
- 중간 전체 테스트 실패는 동시에 실행된 Gradle이 같은 XML 결과 파일을 쓰며 생긴 충돌임을 확인하고 단일 실행으로 재검증했다.

행동: 실제 제품 결함과 테스트 실행 충돌을 구분한 뒤 수정안을 채택했다. Spring 기본 오류 설정 전체를 바꾸는 작업은 별도 범위로 남겼다.

내 최종 선택: 초기 100MB·110MB 정책은 10MB·12MB로 수정했고, 과도한 서버 세부 구현은 제거했으며, multipart 내부 오류 정보는 외부 응답에서 차단했다.

## 7. 구현 모양에 묶인 테스트를 사용자 행동 중심 검증으로 보완하기

보완의 출발점: 정책 조회 화면을 구현한 뒤 테스트가 고정 확장자 개수, 배열 순서, 라이브러리 URL 같은 세부사항까지 확인해 변경에 지나치게 민감해졌다.

질문 1: Axios로 정책을 조회하는 화면을 만들고, 정책 변경·등록·삭제 뒤 최신 DB 상태와 실제 브라우저 요청까지 검증해줘.

AI 답변:

- `next-work-briefing`, `tdd`, 인앱 브라우저를 사용했다.
- Axios WebJar와 정적 JavaScript를 추가해 페이지가 로드될 때 정책 API를 호출하도록 구현했다.
- 고정 정책 체크 상태, 커스텀 목록, 로딩·성공·오류 화면을 만들었다.
- 격리 H2에서 초기 조회와 PATCH·POST·DELETE 후 조회를 통합 테스트로 작성했다.
- 페이지 테스트 Red→Green, 전체 테스트, JavaScript 문법 검사를 통과했다.
- 실제 브라우저 DOM과 Tomcat access log로 GET 요청과 새로고침 결과를 확인했다.

행동: 테스트 코드를 리뷰하니 고정 확장자 7개를 정확히 세고 배열 인덱스로 항목을 찾았으며, 페이지 테스트는 WebJar 버전과 HTML 문자열까지 확인하고 있었다. 카탈로그나 라이브러리 버전 변경이 사용자 동작과 무관하게 테스트를 깨뜨릴 수 있다고 판단했다.

질문 2: 목록 개수와 배열 순서에 묶인 테스트를 줄이고, 인수 테스트 수와 페이지 HTML 단언도 필요한 수준으로 축소해줘.

AI 답변:

- `tdd`와 테스트 전체 구조 검색으로 각 단언이 어떤 계약을 소유하는지 확인했다.
- 초기 정책 통합 테스트는 목록이 비어 있지 않고 모든 항목이 미차단인지 확인하도록 바꿨다.
- 변경 흐름은 원하는 확장자를 이름으로 찾아 상태를 확인하는 하나의 시나리오로 묶었다.
- 페이지 테스트는 JavaScript가 찾는 최소 DOM container만 확인하도록 줄였다.
- 카탈로그의 정확한 개수와 순서는 가장 가까운 원천 테스트 한 곳만 책임지도록 했다.
- 대상 테스트, 전체 테스트, JavaScript 문법 검사와 공백 검사를 통과했다.

행동: 코드 수정은 만족했지만 같은 실수가 다음 테스트에서 반복될 수 있다고 판단했다. 이번 리뷰 기준을 저장소 공통 규칙으로 남기도록 요청했다.

질문 3: 목록 개수·순서, 통합 테스트 기동 범위, 페이지 HTML 단언에 대한 재발 방지 기준을 문서화해줘.

AI 답변:

- `backend-documentation`으로 `AGENTS.md`에 공통 테스트 유지보수 원칙을 추가했다.
- 스프린트 문서에는 카탈로그 계약, 통합 시나리오, 브라우저 smoke가 각각 무엇을 확인하는지 구분했다.
- 문서 브랜치에는 관련 문서만 있는지 검사하고 기능 브랜치에 병합했다.
- 병합 후 전체 테스트와 공백 검사를 통과했다.

행동: 사용자 행동은 통합·브라우저 테스트가 보고, 정확한 카탈로그 값은 원천 테스트 한 곳이 보도록 역할을 나눈 결과를 채택했다.

내 최종 선택: 화면 구현 자체보다 테스트가 무엇을 보장해야 하는지 다시 질문했고, 경직된 테스트를 줄인 뒤 작성 기준까지 남겼다.

## 8. 구현 편의가 섞인 모델 비교를 데이터 불변식 중심 판단으로 보완하기

보완의 출발점: 기본 확장자와 사용자가 추가한 확장자를 각각 다른 테이블에 둘지, 하나의 정책으로 관리할지 결정해야 했다. 기존 코드를 적게 바꾸는 방향이 좋은 설계처럼 보일 위험이 있었다.

질문 1: fixed와 custom을 분리할지 하나의 엔티티와 유형으로 관리할지, 다른 선택지까지 예시와 장단점으로 비교하되 최종 결정은 내리지 마.

AI 답변:

- `adr-predecision-review`와 `skill-creator`를 사용했다.
- fixed/custom 분리 엔티티, 단일 정책 엔티티, 기본 카탈로그와 사용자 정책 분리 모델을 비교했다.
- 데이터 중복, 만들 수 있는 잘못된 상태, 조회 방식, 확장성을 기준으로 장단점을 정리했다.
- 추천 후보는 제시했지만 사용자가 결정할 자리는 비워 둔 문서를 만들었다.

행동: 검토 문서를 읽어보니 현재 구현과 변경 비용이 선택 근거에 섞여 있었다. 초안 설계에서 “지금 코드가 편한가”가 데이터 의미보다 먼저 판단되는 것을 원하지 않았다.

질문 2: 현재 구현 상태와 코드 변경 비용은 선택 근거에서 빼고, 데이터 의미와 불변식만으로 다시 비교해줘.

AI 답변:

- 구현 편의와 변경 비용 문구를 제거했다.
- fixed와 custom이 모두 정규화된 확장자를 차단하는 정책이라는 공통 의미를 중심으로 다시 작성했다.
- 문서가 최종 결정을 포함하지 않는지, 구현 상태를 근거로 삼지 않는지 diff로 확인했다.
- 이 검토 방식을 재사용할 수 있도록 ADR 결정 전 리뷰 skill로 정리했다.

행동: 수정된 선택지를 검토한 뒤 fixed와 custom은 행위가 다를 뿐 같은 정책 개념이라고 판단했다. 중복과 필수값은 DB가 보장하고 유형별 행위는 애플리케이션이 검증하는 단일 모델로 ADR을 확정하도록 요청했다.

질문 3: fixed와 custom을 단일 `ExtensionPolicy`와 유형으로 관리하고, DB와 애플리케이션의 검증 책임을 나눈 ADR을 작성해줘.

AI 답변:

- 단일 엔티티와 `policy_type`을 accepted ADR로 작성했다.
- 확장자 중복과 필수값은 DB 제약, 고정 카탈로그와 유형별 행위는 애플리케이션 검증으로 책임을 분리했다.
- 결정문이 사용자가 확정한 의미와 일치하는지 문서 diff로 확인했다.

행동: ADR 기준으로 기존 논란 코드를 제거하고 처음부터 구현하도록 요청했다. 구현 후에는 별도 AI 세션에서 독립 리뷰를 진행했다.

질문 4: ADR 기준으로 정책 도메인·JPA·초기화·200개 등록 한도를 구현하고, 별도 리뷰에서 나온 누락도 모두 확인해줘.

AI 답변:

- 단일 정책 엔티티, 고정 카탈로그, 커스텀 등록 서비스, quota 행을 구현했다.
- 별도 리뷰에서 soft delete와 물리 삭제 계약 충돌, 고정·커스텀 카탈로그 불변식, 200개 동시 등록, `policy_type` DB 제약, null·unique·정규화 테스트 누락을 찾았다.
- 유형과 상태의 잘못된 조합을 DB `CHECK`로 막았다.
- quota 행을 비관적 잠금해 동시 요청에서도 200개를 넘지 않도록 수정했다.
- 도메인·DB 직접 삽입·초기화·동시성·전체 테스트와 공백 검사를 통과했다.

행동: 리뷰에서 나온 다섯 가지 누락을 모두 반영하고 soft delete 대신 물리 삭제 계약을 문서에도 명시했다. 구현 편의보다 데이터 규칙을 우선한 모델과 검증 결과를 채택했다.

내 최종 선택: 첫 비교 문서의 구현 편향은 제거했고, 선택한 모델도 독립 리뷰에서 발견한 DB·동시성 누락을 보완한 뒤 사용했다.
