# 스프린트 2 PRD: 업로드 정책 신뢰성·보안·운영 완성

Status: implementation-complete-with-deferred-decisions

Issue tracker: local Markdown

## Problem Statement

스프린트 1은 확장자 denylist와 기본 파일 저장 흐름을 제공하지만, 허용 문자 검증, 요청 용량 제한, MIME 기반 안전 형식 검증, 저장 경로 운영 설정, 정책 변경 감사, 오류 추적, 업로드 메타데이터 상태, 원자적 파일 확정, 멱등 재시도, 정책 집합 기반 allowlist 전환 준비가 아직 완성되지 않았다.

사용자는 업로드가 왜 거부됐는지 안전하게 알 수 있어야 하고, 운영자는 오류와 정책 변경을 추적할 수 있어야 한다. 또한 네트워크 응답 유실·프로세스 중단·동시 재시도에도 부분 파일이나 중복 파일을 남기지 않고 업로드 결과를 일관되게 확인할 수 있어야 한다. 스프린트 2는 [ADR 구현 상태 점검](../../adr/adr-implementation-status-review-2026-08-30.md)에서 미완료로 분류된 모든 ADR을 완료 목표로 한다.

## Solution

업로드 요청을 다음 순서로 안전하게 처리한다: multipart 크기 제한 → 파일 part 하나 검증 → 원본 파일명의 모든 확장자 구간 추출·확장자 규칙 검증 → 콘텐츠 기반 MIME과 허용 형식 호환성 검증 → 정책 평가 → 업로드 메타데이터와 멱등 기록 저장 → 임시 파일 저장 → atomic move → 완료 상태와 재사용 가능한 결과 저장 → 안전한 성공 또는 오류 응답 반환.

정책 변경은 현재 상태 변경과 append-only 이력을 하나의 트랜잭션으로 기록한다. 업로드 오류는 `requestId`, 안정적인 오류 코드, 안전한 context를 제공하고 FE가 사용자 메시지를 조립한다. 장기적으로는 정책 집합·적용 범위·판정 결과를 도입해 allowlist 전환을 단계적으로 수행할 수 있게 한다.

## User Stories

1. 관리자로서 커스텀 확장자를 비어 있지 않고 20자 이내이며 점을 포함하지 않는 값으로 등록하고 싶다. 정책 값의 의미를 일관되게 유지하기 위해서다.
2. 업로드 사용자로서 특수문자나 복합 확장자로 위장한 파일이 거부되는 이유를 알고 싶다. 안전하지 않은 파일을 다시 시도하지 않기 위해서다.
3. 업로드 사용자로서 10MB보다 큰 파일이 저장 전에 거부되기를 원한다. 서버 자원을 불필요하게 사용하지 않기 위해서다.
4. 운영자로서 개발·테스트·운영 환경별 저장 루트를 설정하고 싶다. 코드 수정 없이 저장소를 운영하기 위해서다.
5. 업로드 사용자로서 파일 이름을 바꾼 실행 파일이나 지원하지 않는 MIME 파일이 거부되기를 원한다. 허용되지 않은 콘텐츠를 업로드하지 않기 위해서다.
6. 업로드 사용자로서 원래 파일명과 업로드 결과를 확인하고 싶다. 서버 저장 파일명과 내 파일을 구분하기 위해서다.
7. 운영자로서 저장 중단 후에도 업로드가 접수·완료·실패 중 무엇인지 확인하고 싶다. 고아 파일과 미완료 레코드를 복구하기 위해서다.
8. 업로드 사용자로서 성공 응답이 유실돼도 같은 업로드를 다시 전송했을 때 파일이 중복 저장되지 않기를 원한다. 결과를 안전하게 복구하기 위해서다.
9. 업로드 사용자로서 처리 중인 같은 요청에 재시도 안내를 받고 싶다. 중복 저장 없이 결과를 확인하기 위해서다.
10. 운영자로서 업로드 오류의 `requestId`로 로그를 찾고 싶다. 문의와 서버 처리를 연결하기 위해서다.
11. 프런트엔드 개발자로서 오류 코드와 제한된 context로 사용자 메시지를 조립하고 싶다. 서버 문구 변경에 화면이 깨지지 않게 하기 위해서다.
12. 운영자로서 누가 어떤 경로로 정책을 만들고, 변경하고, 삭제했는지 알고 싶다. 업로드 차단 원인을 추적하기 위해서다.
13. 운영자로서 삭제된 커스텀 정책도 과거 이력에서 확인하고 싶다. 삭제 후 재등록과 신규 등록을 구분하기 위해서다.
14. 정책 소유자로서 전역 denylist와 allowlist를 혼동하지 않고 관리하고 싶다. 정책 결과를 설명 가능하게 만들기 위해서다.
15. 조직 관리자나 사용자 정책 소유자로서 정책 집합을 적용 범위에 연결하고 싶다. 정책 행을 사용자마다 복제하지 않기 위해서다.
16. 운영자로서 allowlist 전환 전에 shadow 평가 결과를 확인하고 싶다. 정상 업무 파일이 갑자기 차단되는 일을 피하기 위해서다.
17. 운영자로서 문제가 발생하면 일부 범위를 기존 denylist로 되돌리고 싶다. 업무 중단을 최소화하기 위해서다.
18. 보안 담당자로서 기존 완료 파일은 새 allowlist 전환만으로 소급 차단되지 않기를 원한다. 정책 전환과 파일 접근 통제를 분리하기 위해서다.
19. 개발자로서 각 보안·상태·재시도 규칙을 독립된 모듈로 테스트하고 싶다. 변경 후에도 업로드 흐름을 신뢰하기 위해서다.
20. 프로젝트 소유자로서 스프린트 2 종료 시 미완료 ADR마다 코드, 계약, 테스트, 문서 중 무엇이 완료됐는지 확인하고 싶다. 완료를 문서 상태만으로 오인하지 않기 위해서다.

## Implementation Decisions

- 스프린트 범위는 ADR 0005, 0006, 0009, 0011, 0012, 0013, 0014, 0015, 0016의 미완료 결정과 ADR 0010의 보류 상태를 포함한다.
- ADR 0010의 한글·영문·숫자 전용 확장자 제한은 이번 스프린트에서 구현하지 않고 보류한다. 현재의 빈 값·20자·점 검증은 유지하며, 전체 원본 파일명 제한은 도입하지 않는다.
- 확장자 검증은 원본 파일명의 모든 확장자 구간에 적용한다. 원본 파일명 메타데이터와 길이는 ADR 0006에서 별도로 다룬다.
- 요청 크기는 multipart 파싱 단계에서 파일 10MB, 전체 요청 12MB로 제한한다. 초과 요청은 정책·MIME·저장 로직을 실행하지 않고 413 의미의 안전한 오류로 변환한다.
- 업로드 API는 `file` part 하나만 허용한다. 두 개 이상이면 정책·MIME·저장 로직을 실행하지 않고 `400 MULTIPLE_FILES_NOT_ALLOWED`로 거부한다.
- 저장 루트는 운영자 설정으로 주입하며 기본값은 기존 `./uploads`다. HTTP 입력과 원본 파일명은 저장 경로를 결정하지 않는다.
- MIME 검증은 Apache Tika의 콘텐츠 감지와 애플리케이션 소유의 실행 MIME denylist로 분리한다. `.txt`·`text/plain`은 허용하며, 확장자와 MIME이 다르다는 사실만으로는 차단하지 않는다. Parser·악성코드 검사·외부 바이러스 스캔은 도입하지 않는다.
- 실행 가능한 바이너리 MIME는 `application/x-dosexec`, `application/x-msdownload`, `application/x-executable`, `application/x-elf`, `application/x-mach-binary`, `application/x-sharedlib`, `application/java-archive`, `application/x-java-archive`로 확정한다. `application/octet-stream` 등 분석이 완료된 `UNKNOWN` MIME은 경고 로그 후 허용한다. Tika 분석 자체가 `IOException`으로 실패한 `FAILED` 결과는 `FILE_TYPE_DETECTION_FAILED`로 거부한다. 상세 결정은 ADR 0018을 따른다.
- 업로드 메타데이터는 원본 파일명, 서버 저장 파일명, 처리 상태를 보존한다. 원본 파일명은 표시용이고 저장 경로·파일 시스템 식별자·공개 인증 정보로 사용하지 않는다.
- 원본 파일명은 basename만 보존하며 빈 값·NUL·제어문자를 거부하고, 최대 255 Unicode code point를 허용한다. 서버 저장 파일명은 UUID와 검증된 최종 확장자로 계속 생성한다.
- 업로드 상태는 `RECEIVING`, `COMPLETED`, `FAILED`로 관리한다. 검증이 통과한 뒤 `RECEIVING`을 먼저 커밋하고, 같은 파일시스템의 임시 경로에 저장한 후 atomic move로 최종 파일을 확정한다. `COMPLETED` 커밋 후에만 201을 반환한다.
- stale `RECEIVING`은 30분 이상 갱신되지 않은 레코드로 판단하고, 1분 주기 정리 작업에서 파일 존재·상태를 대조한다. 최종 파일이 있으면 완료 처리하고, 임시 파일만 있거나 파일이 없으면 실패 처리·정리한다.
- `Idempotency-Key`는 FE가 논리적 업로드 시작 시 UUID v4로 생성하고 재시도 동안 유지한다. 헤더 값은 업로드 `requestId`로 사용하며, 원본 파일명·확장자·requestId를 별도 지문으로 저장하지 않는다.
- 동일 requestId의 완료 요청은 새 파일을 만들지 않고 저장된 결과를 반환한다. 처리 중 동일 requestId는 저장을 다시 시작하지 않고 `409 IDEMPOTENCY_IN_PROGRESS`를 반환한다. 실패한 동일 requestId는 저장된 실패 결과를 반환한다.
- 처리 중 응답은 `409 Conflict`와 `Retry-After`를 사용한다. 서버가 중복 요청 관찰 횟수에 따라 최소 1초·최대 30초의 capped exponential backoff와 jitter를 계산하며, FE는 최대 3회·전체 30초까지만 자동 재시도한다.
- 업로드 오류 응답은 `code`, requestId, 안전한 `context`를 중심으로 한다. 서버 `message`는 호환 기간에만 유지할 수 있고, FE는 코드·context로 문구를 조립한다. 로그에는 requestId, 오류 코드, HTTP 상태, 처리 결과를 구조화해 남긴다.
- 정책 생성·고정 정책 변경·커스텀 삭제는 현재 상태 변경과 append-only 감사 이력을 같은 트랜잭션에서 기록한다. 이력에는 시각, 정책 식별자·확장자, action, 이벤트 후 `BLOCKED`·`UNBLOCKED` 상태, actor 또는 `SYSTEM`을 남긴다. 현재 정책 API에는 변경 경로와 requestId를 추가하지 않는다.
- allowlist 전환은 기존 전역 denylist를 즉시 대체하지 않는다. 정책 집합은 `DENYLIST` 또는 `ALLOWLIST` mode를 명시하고, 정책 항목과 적용 관계를 분리한다. 신규 업로드만 새 정책의 대상이며 기존 완료 파일은 소급 평가하지 않는다.
- ADR 0016은 현재 `proposed`이며 allowlist 전환 조건이 확정되기 전에는 구현하지 않는다. ADR 0006은 이번 작업에서 채택하고 원본 파일명 메타데이터를 영속화한다.
- ADR 0016 구현 게이트는 전역 강제 차단 override 여부, 정책 집합이 없는 대상의 기본 mode, allowlist 소유자·승인자, shadow 평가 기간과 허용 거부율, 적용 범위 우선순위의 명시적 결정이다. 이 게이트가 닫히기 전에는 policy-set 스키마·API·실제 allowlist 차단을 확정하지 않는다.
- 완료 시 API 계약, 스프린트 문서, ADR 상태, 구현 상태 점검 문서를 실제 구현과 동기화한다.

## Testing Decisions

- 테스트는 private 구현이 아니라 외부에서 관찰 가능한 정책 판정, HTTP 상태·응답, DB 상태, 파일 시스템 결과, 재시도 결과를 검증한다.
- 확장자 값 객체는 기존 정규화, 빈 값, 20자 경계, 점 거부 동작을 회귀 테스트한다. ADR 0010의 허용 문자 확대·축소 테스트는 보류한다.
- MIME 검증 모듈은 실행 MIME 차단, `.txt`·`text/plain` 허용, 실행 파일 위장, `UNKNOWN` MIME 경고·허용, `FAILED` MIME 감지 실패 거부를 단위 테스트한다. 실제 Tika 입력 fixture는 작은 고정 파일을 사용한다.
- multipart 제한은 10MB 경계와 12MB 요청 경계에서 서비스·저장소가 호출되지 않고 413 오류 계약이 반환되는지 통합 테스트한다. 파일 part가 두 개 이상인 요청은 서비스·저장소를 호출하지 않고 `400 MULTIPLE_FILES_NOT_ALLOWED`를 반환하는지 통합 테스트한다.
- 저장 루트는 기본 경로와 설정 override를 통합 테스트하고, 원본 파일명이 경로 조작에 사용되지 않는지 확인한다.
- 업로드 메타데이터와 상태 전이는 receiving 선저장, 임시 파일 쓰기, atomic move, completed 전환, 저장 실패 시 failed 전환을 통합 테스트한다. 프로세스 중단을 직접 재현하지 못하는 경우에는 복구 서비스가 stale 상태·파일 조합별로 수행하는 외부 결과를 단위 테스트한다.
- 멱등성은 같은 키의 성공 결과 재사용, 같은 키에 다른 파일이 와도 지문 비교 없이 기존 결과를 사용하는 정책, 처리 중 중복 요청의 비저장, 응답 유실 뒤 재요청, stale 복구 뒤 재처리를 통합 테스트한다.
- 오류 계약은 requestId 형식, context의 허용 필드, 내부 경로·stack trace 비노출, FE 코드 기반 메시지 표시를 controller와 브라우저 smoke로 검증한다.
- 감사 이력은 정책 생성·수정·삭제마다 action과 이벤트 후 상태가 같은 트랜잭션으로 기록되고, 현재 상태 변경 실패 시 이력도 남지 않는지 JPA·통합 테스트한다. `BLOCKED_CHANGED`의 이전 상태는 직전 이력과 비교해 해석한다.
- policy-set과 allowlist는 mode별 판정, scope 우선순위, global 강제 차단, shadow 결과, denylist 복귀를 도메인 단위 테스트로 먼저 고정하고 API 흐름을 통합 테스트한다.
- 기존 테스트 관례대로 한글 `@DisplayName`과 given/when/then 주석을 사용한다. 고정 카탈로그의 개수·순서는 원천 카탈로그 또는 초기화 테스트 한 곳에서만 단언한다.

## Out of Scope

- 문서 Parser, 바이러스 검사, 샌드박스 격리, 외부 악성코드 검사 인프라
- S3·MinIO 같은 외부 오브젝트 스토리지로의 이전
- 파일 다운로드·미리보기·삭제·보존 기간·소유권·접근 제어의 완전한 제품 기능
- 사용자 인증·조직 관리 자체의 도입
- 기존 완료 파일의 allowlist 소급 차단 또는 재검사

- 완전한 관측 플랫폼, 분산 추적, 장기 로그 저장소 도입

## Further Notes

- 이 PRD는 모든 미완료 ADR을 스프린트 2의 완료 목표로 묶지만, 미결 제품·운영 결정까지 코드로 추정하지 않는다. 결정 게이트의 결과가 채택·변경·철회 중 무엇이든 ADR과 API 계약에 먼저 반영해야 한다.
- 구현 순서는 입력·자원 보호(0009, 0011) → 실행 MIME denylist(0005) → 오류 추적·감사(0013, 0012) → 메타데이터·상태 확정(0006, 0014) → 멱등 재시도(0015) → policy-set·allowlist 전환 준비(0016)를 권장한다. ADR 0010은 보류한다.
- 상세 작업 순서, 작업별 Red/Green 검증, 시작 전 질문과 중단 규칙은 [스프린트 2 구현 순서·결정 게이트 체크리스트](sprint-2-implementation-checklist.md)를 따른다.
- `implementation-complete-with-deferred-decisions`는 ADR 0005·0006·0009·0011·0012·0013·0014·0015의 구현이 완료됐고, ADR 0010·0016과 접근성 수동 검증은 의도적으로 대기 중이라는 의미다. ADR 0016은 사용자 또는 제품 소유자가 결정 게이트를 닫기 전에는 구현을 시작하지 않는다.
