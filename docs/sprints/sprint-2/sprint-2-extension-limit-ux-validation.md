# 스프린트 2: 확장자 정책 한도 UX 검증

스프린트 전체 구현 순서와 시작 전 결정 게이트는 [스프린트 2 구현 순서·결정 게이트 체크리스트](sprint-2-implementation-checklist.md)를 따른다. 이 문서는 그중 최종 UX·접근성 검증 범위만 관리한다.

> 상태: 주요 브라우저 검증 완료·VoiceOver 및 실제 200% 확대 검증 대기

## 스프린트 목표

스프린트 1에서 구현한 커스텀 확장자 최대 길이 20자와 최대 등록 수 200개가 실제 관리자 화면에서 사용 가능한지 검증한다. 검증 결과에 따라 현재 정책을 유지하거나 UX 개선·검색·페이징 도입 여부를 결정한다.

이번 스프린트에서는 20자와 200개를 새로운 값으로 변경하지 않는다. 현재 API 계약과 구현을 기준으로 경계값을 실제 화면에 적용하고, 그 결과를 근거로 후속 작업을 결정한다.

## 왜 하는가

20자는 일반적인 단일 확장자를 충분히 표현하면서 입력·표시 길이를 제한하는 값이다. 200개는 DB 조회 성능의 절대 한계라기보다 현재처럼 전체 목록을 한 번에 조회하고 검색·페이징 없이 관리하는 화면의 운영 상한이다.

두 값의 적절성은 코드에 상수가 존재하는 것만으로 확인할 수 없다. 실제 최대 길이 입력과 최대 목록 크기를 브라우저에서 확인해 레이아웃, 탐색성, 오류 복구, 응답·렌더링 부담을 검증해야 한다.

## 검증 요구사항

### 1. 20자 확장자 입력

- 정규화 후 20자인 영문·숫자·한글 입력을 준비한다.
- 데스크톱과 모바일 화면에서 입력창, 오류 영역, 정책 목록의 줄바꿈·말줄임·겹침 여부를 확인한다.
- 20자 입력이 정상 등록되고 조회·삭제 흐름에서 동일하게 표시되는지 확인한다.
- 21자 입력은 저장되지 않고, 사용자가 원인을 이해할 수 있는 입력 오류를 표시하는지 확인한다.
- 실패 후 입력값이 불필요하게 사라지지 않는지 확인한다.

### 2. 200개 정책 목록

- 테스트 데이터 또는 API를 사용해 커스텀 정책 200개를 준비한다.
- 전체 목록 조회 후 화면의 스크롤, 항목 탐색, 삭제 버튼 조작, 빈 상태 전환을 확인한다.
- 데스크톱과 모바일에서 목록이 관리 가능한지, 화면이 깨지거나 조작 대상이 지나치게 작아지지 않는지 확인한다.
- 응답 크기와 브라우저 렌더링 지연을 확인한다. 성능 측정은 관리성 판단을 보완하는 근거로 사용한다.
- 200개에 도달했을 때 현재 등록 수와 최대 등록 수를 사용자가 알 수 있는지 확인한다.

### 3. 201번째 등록

- 200개가 등록된 상태에서 201번째 커스텀 확장자 등록을 시도한다.
- 서버가 등록을 거부하고 `409 CUSTOM_LIMIT_EXCEEDED`를 반환하는지 확인한다.
- 화면이 사용자용 한도 초과 메시지를 표시하고, 입력한 확장자 값을 보존하는지 확인한다.
- 동시 요청으로 한도에 도달한 경우에도 서버 응답을 기준으로 목록을 재조회하고 화면 상태를 복구하는지 확인한다.

### 4. 접근성·반응형 최소 검증

- 키보드만으로 정책 조회·체크·추가·삭제·업로드를 완료할 수 있는지 확인한다.
- VoiceOver 또는 NVDA에서 입력 이름, 업로드 중 상태, 성공·실패 메시지가 전달되는지 확인한다.
- 브라우저 200% 확대와 320px 화면 폭에서 가로 스크롤·요소 겹침·버튼 조작 불가 여부를 확인한다.
- 20자 확장자와 긴 오류 메시지가 화면 밖으로 잘리지 않고 줄바꿈되는지 확인한다.
- 항목 삭제나 업로드 실패 후 키보드 포커스가 사라지지 않고 재시도할 수 있는지 확인한다.
- 색상만으로 성공·실패를 구분하지 않는지 확인한다.

## 판정 기준과 후속 결정

- 20자와 200개에서 레이아웃·탐색·오류 복구에 문제가 없으면 현재 값을 유지한다.
- 접근성·반응형 검증에서 문제가 발견되면 해당 문제를 최소 UX 개선 작업으로 분리하고, 전체 UI 프레임워크 교체나 완전한 접근성 인증 범위로 확대하지 않는다.
- 긴 입력 표시가 불편하면 줄바꿈·말줄임·입력 안내 등 필요한 최소 UX만 별도 구현 항목으로 만든다.
- 200개 목록의 탐색성이 떨어지면 검색·서버 페이징·정렬·일괄 작업의 필요성을 별도로 검토한다.
- 응답·렌더링 문제가 확인되더라도 200개를 DB 성능의 절대 한계로 표현하지 않고, 측정 환경과 데이터 조건을 함께 기록한다.
- 20자·200개를 장기적인 비즈니스 불변식으로 확정하거나, 200개 이후 페이징 전환 기준을 정책으로 고정할 때만 ADR 작성 여부를 결정한다.

## 2026-08-31 검증 결과

- 실행 환경: Codex In-app Browser, 기본 유효 폭 `1280x720`, 반응형 `320x700`, 200% 확대 유효 폭 대체 검증 `640x720`; 격리 H2 DB와 임시 파일 저장 경로를 사용했다.
- 20자 입력: `uxabcdefghijklmnopqr` 등록 성공, 조회·삭제 성공. 21자 입력 `uxabcdefghijklmnopqrs`는 `INVALID_EXTENSION`으로 저장되지 않고 입력값을 보존했다.
- 200개 목록: API로 `ux001`~`ux200`을 생성했다. 응답 크기는 1,873 bytes였고, 200개 항목을 렌더링했으며 기본 폭과 320px 폭 모두 `scrollWidth == clientWidth`였다. 마지막 항목 삭제 후 199개와 빈 상태 전환을 확인했다.
- 201번째 등록: `409 CUSTOM_LIMIT_EXCEEDED`, 입력값 보존, 200개 목록 유지 및 한국어 한도 안내를 확인했다.
- 업로드: 정상 `.txt`는 서버 생성 파일명으로 성공했다. 실행 MIME 파일은 `422 BLOCKED_EXECUTABLE_MIME`, 11MiB 파일은 `413 FILE_SIZE_EXCEEDED`로 거부됐고 내부 경로·stack trace는 화면에 노출되지 않았다.
- 멱등성: 동일 UUID v4 requestId 동시 업로드에서 한 요청은 `201`, 다른 요청은 `409 IDEMPOTENCY_IN_PROGRESS`와 `Retry-After: 2`를 반환했다.
- UX 수정: 정책 오류 code 기반 한국어 안내와 정책 삭제·업로드 실패 후 입력 컨트롤 포커스 복귀를 구현하고 재검증했다. 관련 코드 커밋은 `a840db2`다.
- 접근성: DOM의 입력·버튼은 native tab order와 label/aria-label을 갖고, 오류 후 컨트롤은 활성화됐다. IAB 자동화에서 Tab/Enter 키 이벤트가 실제 포커스 이동·제출로 진행되지 않았고 VoiceOver는 실행하지 못했으므로 키보드 전용 완료와 스크린리더 결과는 미확정이다. 실제 브라우저 200% zoom API도 제공되지 않아 `640px` 유효 폭 대체 결과만 기록한다.
- 후속 결정: 현재 20자·200개 값은 유지한다. 검색·페이징·ADR 추가는 하지 않는다. VoiceOver, 실제 200% 확대, 409 화면 분기는 별도 수동 환경 또는 브라우저 기능 확보 후 보완한다.

## 결과 기록

검증 결과에는 다음 정보를 남긴다.

- 테스트 데이터 생성 방식과 실제 입력값
- 브라우저·화면 크기·실행 환경
- 20자, 200개, 201개 경계별 관찰 결과
- 키보드·스크린리더·확대·모바일 반응형 검증 결과
- 응답 크기와 렌더링 부담을 측정했다면 측정 방법과 결과
- 유지·UX 개선·검색/페이징·ADR 작성 여부에 대한 후속 결정

상세 결과와 판단 근거는 [제한값 근거와 UX 분석](../../../.internal-docs/file-upload-risk-analysis/11-limit-rationale-and-ux.md) 및 [`PROMPT_LOG.md`](../../../PROMPT_LOG.md)에 반영한다.

## 범위 외

- 검증 전 20자·200개 값을 임의로 변경하지 않는다.
- quota 변경 API나 사용자별·조직별 quota를 추가하지 않는다.
- 검색·페이징은 검증 결과 필요성이 확인된 경우에만 후속 요구사항으로 전환한다.
- 이번 스프린트에서 완전한 WCAG 준수나 새로운 UI 프레임워크 도입을 별도 목표로 삼지 않는다.
- 검증 계획 자체를 ADR로 만들지 않는다. 검증 결과로 장기 정책을 확정할 때 ADR을 검토한다.
