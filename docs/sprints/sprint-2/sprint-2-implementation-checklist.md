# 스프린트 2 구현 순서·결정 게이트 체크리스트

> 상태: 계획 수립 완료·구현 대기
>
> 기준 문서: [스프린트 2 PRD](../../../.scratch/sprint-2/PRD.md), [ADR 구현 상태 점검](../../adr/adr-implementation-status-review-2026-08-30.md)

## 사용 규칙

- 체크리스트는 위에서 아래 순서로 진행한다. 선행 작업이 끝나지 않은 작업은 시작하지 않는다.
- 각 작업의 `시작 전 질문`이 남아 있으면 코드·설정·API를 변경하지 않는다. 질문 문서에 배경·선택지·영향·예시를 기록하고 사용자 답변을 받은 뒤 해당 항목을 시작한다.
- 질문의 답변이 기존 ADR을 변경하면 먼저 ADR과 API 계약을 문서 브랜치에서 갱신한다. `proposed` ADR은 채택·변경·철회 중 하나로 확정되기 전에는 구현하지 않는다.
- 모든 구현 작업은 한글 `@DisplayName`의 Red 테스트부터 시작해 최소 Green 구현, 리팩터링, 관련 테스트, 전체 `./gradlew test` 순서로 확인한다.
- 기능 코드와 문서를 같은 직접 커밋에 섞지 않는다. 문서는 `docs` 브랜치에서, 기능 코드는 문서 병합 뒤 `feat/<작업명>` 브랜치에서 진행한다.

## 전체 흐름

```text
문서·결정 게이트
  → 입력·자원 보호 (0010, 0009, 0011)
  → MIME 정책 확정·검증 (0005)
  → 오류 추적·정책 감사 (0013, 0012)
  → 파일 메타데이터·상태 확정 (0006, 0014)
  → 멱등 재시도 (0015)
  → 정책 집합·allowlist 전환 (0016)
  → 브라우저 UX·최종 회귀 검증
```

## 0. 스프린트 기준선과 문서 동기화

- [ ] PRD, ADR 구현 상태 점검, 기존 스프린트 2 UX 검증 문서의 범위를 대조한다.
- [ ] 이 체크리스트를 문서 인덱스에 반영하고 `PROMPT_LOG.md`에 계획 수립 근거를 기록한다.
- [ ] `docs` 브랜치의 문서 변경만 커밋·push한 뒤, `main` 최신 기준에서 기능 브랜치를 만들고 문서 커밋을 병합한다.
- [ ] 기능 브랜치의 시작점에서 전체 테스트를 실행해 기존 실패가 없는지 기록한다.

시작 전 질문: 없음. 기존 사용자 결정과 문서 기준을 확인하는 단계다.

완료 기준: 구현에 사용할 문서 기준과 브랜치가 확정되고, 기준선 테스트 결과가 기록된다.

## 1. ADR 0010 — 확장자 허용 문자 완성

- [ ] 한글·영문·숫자만 허용하고 공백·점·경로 구분자·기타 특수문자를 거부하는 값 객체 테스트를 먼저 작성한다.
- [ ] 정책 등록과 업로드 파일명 추출이 같은 값 객체 검증 결과를 사용하는지 회귀 테스트한다.
- [ ] 최소 검증 구현 후 기존 정규화·20자 제한·고정 확장자 카탈로그 동작이 유지되는지 확인한다.

시작 전 질문: 없음. ADR 0010의 허용·거부 범위가 확정되어 있다.

완료 기준: 유효 입력은 정규화되어 저장·비교되고, 허용되지 않은 문자는 `INVALID_EXTENSION`으로 일관되게 거부된다.

## 2. ADR 0009 — multipart 용량 제한과 413 계약

- [ ] 파일 100MB, 요청 전체 110MB 제한의 설정 테스트와 용량 초과 시 서비스가 호출되지 않는 HTTP 테스트를 작성한다.
- [ ] multipart 용량 초과 예외가 넓은 파일 입력 오류 처리보다 먼저 413으로 변환되도록 구현한다.
- [ ] 프런트가 용량 초과 오류를 안전하게 표시하는지 확인한다.

시작 전 질문:

- 용량 초과의 안정적인 오류 코드를 무엇으로 할 것인가? 권장값은 `FILE_SIZE_EXCEEDED`다.
- 업로드 오류의 장기 응답 형식은 ADR 0013 작업 전까지 기존 `code`·`message`를 유지할 것인가, 이 작업부터 `requestId`·`context` 형식을 함께 도입할 것인가?

중단 규칙: 위 오류 코드와 응답 형식이 확정되기 전에는 413 handler와 API 계약을 구현하지 않는다.

완료 기준: 경계 초과 요청은 확장자·MIME·파일 저장 전에 413과 확정된 오류 계약으로 거부된다.

## 3. ADR 0011 — 저장 루트 설정 외부화

- [ ] 기본 저장 루트와 테스트용 override 경로를 검증하는 통합 테스트를 작성한다.
- [ ] 운영자 설정 `file.upload.storage-path`를 저장소에 주입하고 기본값 `./uploads`를 유지한다.
- [ ] 경로 접근 실패가 기존 파일 저장 실패 의미를 유지하는지 확인한다.

시작 전 질문: 없음. 설정 키·기본값·실패 의미가 ADR 0011에 확정되어 있다.

완료 기준: 코드 변경 없이 환경별 저장 경로를 바꿀 수 있고, 원본 파일명이나 HTTP 요청은 물리 경로를 바꾸지 못한다.

## 4. ADR 0005 — MIME allowlist 결정 문서

- [ ] 지원 후보 형식·MIME·위장 파일 위험을 조사해 질문 문서를 작성한다.
- [ ] 사용자 답변을 API 계약과 ADR 보완 문서에 반영한다.
- [ ] 확정된 매핑을 기준으로 이후 검증 테스트 fixture를 준비한다.

시작 전 질문:

- 스프린트 2에서 허용할 정확한 확장자와 MIME 조합은 무엇인가?
- `text/plain`처럼 콘텐츠만으로 강하게 식별하기 어려운 형식은 허용할 것인가? 허용한다면 어떤 확장자와 조합할 것인가?
- MIME 불일치, 미지원 형식, 감지 실패의 오류 코드와 사용자 안내는 각각 무엇인가?

중단 규칙: 확장자↔MIME 호환표가 사용자 승인으로 확정되기 전에는 Tika 의존성이나 차단 로직을 추가하지 않는다.

완료 기준: 질문 문서의 답변이 API 계약과 ADR에 반영되고, 다음 구현 작업에서 사용할 허용표가 하나로 확정된다.

## 5. ADR 0005 — 콘텐츠 기반 MIME 검증 구현

- [ ] 허용 조합, 확장자 위장, 감지 실패, 미지원 형식의 Red 테스트를 작성한다.
- [ ] Tika 콘텐츠 감지와 애플리케이션 소유 호환표를 분리한 검증 모듈을 구현한다.
- [ ] MIME 검증이 확장자 정책 판정과 파일 저장보다 먼저 실패하고, 내부 감지 정보가 외부 오류에 노출되지 않는지 확인한다.

시작 전 질문: 작업 4의 세 질문이 모두 문서로 확정되었는지 확인한다. 미확정이면 작업 4로 돌아간다.

완료 기준: 승인된 비실행 파일 형식만 확장자와 실제 MIME의 호환성까지 만족할 때 업로드된다.

## 6. ADR 0013 — 업로드 오류 requestId·context·FE 메시지

- [ ] 업로드 오류에 requestId와 최소 context가 포함되고, 내부 경로·원본 파일명·stack trace가 노출되지 않는 controller 테스트를 작성한다.
- [ ] requestId 생성·로그 상관관계·오류 응답 조립을 공통 경계로 구현한다.
- [ ] FE가 서버 `message`가 아닌 오류 코드와 context로 업로드 안내를 표시하도록 browser smoke를 추가한다.

시작 전 질문:

- requestId의 형식과 생성 방식은 무엇으로 할 것인가? UUID·ULID 등 형식 선택이 필요하다.
- 기존 `message` 필드를 어느 시점까지 호환용으로 유지할 것인가?
- `context`에 각 오류 코드별로 공개 가능한 필드는 무엇인가?
- 구조화 로그의 출력 형식과 보존 위치는 현재 애플리케이션 로그로 충분한가?

중단 규칙: 외부 오류에 노출할 context와 `message` 호환 기간이 정해지기 전에는 응답 DTO·FE 분기 계약을 변경하지 않는다.

완료 기준: 사용자 메시지 책임은 FE에 있고, 운영자는 requestId·오류 코드·상태로 한 요청의 오류를 추적할 수 있다.

## 7. ADR 0012 — 정책 변경 append-only 감사 이력

- [ ] 정책 생성·고정 상태 변경·커스텀 삭제의 전후 값을 기록하는 JPA·통합 테스트를 작성한다.
- [ ] 현재 정책 변경과 감사 이력을 같은 트랜잭션으로 저장한다.
- [ ] 실패 시 현재 정책과 이력 중 하나만 남지 않는지 확인한다.

시작 전 질문:

- 감사 action의 정확한 목록과 명명 규칙은 무엇인가? 최소 후보는 `INITIALIZED`, `CREATED`, `BLOCKED_CHANGED`, `DELETED`다.
- 인증이 없는 현재 단계에서 actor는 모든 요청에 `SYSTEM`으로 기록할 것인가, 별도 변경 경로 값을 함께 둘 것인가?
- 감사 이력의 조회 API·관리자 화면은 이번 스프린트의 완료 범위에 포함하지 않는다는 ADR의 범위 제외를 유지할 것인가?

중단 규칙: action·actor·변경 경로의 저장 의미가 정해지기 전에는 이력 스키마를 만들지 않는다.

완료 기준: 정책의 현재 상태와 감사 이력이 원자적으로 남고, 물리 삭제된 커스텀 정책도 삭제 사실을 추적할 수 있다.

## 8. ADR 0006 — 원본 파일명 메타데이터 채택 결정

- [ ] `proposed` ADR 0006을 채택·변경·철회 중 하나로 결정하는 질문 문서를 작성한다.
- [ ] 채택하면 원본 파일명 길이·basename·제어문자 정책과 공개 응답 범위를 API 계약에 명시한다.
- [ ] 채택 결과에 맞춰 ADR 상태와 PRD·체크리스트 의존성을 갱신한다.

시작 전 질문:

- 원본 파일명 매핑을 스프린트 2에 실제 영속화할 것인가?
- 업로드 성공 응답에 원본 파일명 또는 공개 식별자를 추가할 것인가, 기존 서버 저장 파일명만 유지할 것인가?
- 원본 파일명의 255 code point 검증과 경로 basename 정책을 그대로 채택할 것인가?

중단 규칙: `proposed` ADR이 채택되기 전에는 `UploadFile` 엔티티나 테이블을 추가하지 않는다.

완료 기준: 원본 파일명 메타데이터 정책의 최종 상태가 문서로 확정된다. 채택 시 작업 9로, 철회 시 0014·0015의 대체 상태 모델을 다시 결정한다.

## 9. ADR 0006·0014 — 업로드 메타데이터·임시 파일·상태 전이

- [ ] `RECEIVING` 선저장, 임시 파일 쓰기, atomic move, `COMPLETED` 전환, `FAILED` 전환의 상태 테스트를 먼저 작성한다.
- [ ] 메타데이터 엔티티·저장소와 상태 전이를 구현한다.
- [ ] 입력·정책·MIME 검증 실패가 레코드와 물리 파일을 만들지 않는지 확인한다.
- [ ] stale 레코드와 임시·최종 파일의 조합을 복구 서비스 단위 테스트로 검증한다.

시작 전 질문:

- stale `RECEIVING` 판정 시간, 복구 실행 주기, 재처리 횟수, 메타데이터·파일 보존 기간은 얼마인가?
- 최종 파일은 존재하지만 `COMPLETED` 전환이 실패한 경우, 복구가 무결성 확인 후 완료 처리할 것인가 아니면 실패·정리할 것인가?
- 임시 파일은 저장 루트 아래 어느 경로에 둘 것인가?
- 정리 작업의 실행 주체와 실패 재시도 방식은 무엇인가?

중단 규칙: 상태 복구와 정리의 수명주기가 확정되기 전에는 scheduler나 삭제 로직을 구현하지 않는다. 임시 저장·상태 전이의 기본 흐름만 분리 가능한지 먼저 문서로 판단한다.

완료 기준: 최종 경로에는 완료 파일만 존재하고, DB 상태로 미완료 업로드를 식별·복구·정리할 수 있다.

## 10. ADR 0015 — 멱등키와 재시도

- [ ] 같은 키·같은 요청의 결과 재사용, 같은 키·다른 요청 충돌, 처리 중 중복 요청 비저장, 응답 유실 뒤 재요청의 테스트를 작성한다.
- [ ] 멱등 기록과 요청 지문 검증, 성공 결과 재사용, 처리 중 상태 응답을 구현한다.
- [ ] FE가 논리적 업로드마다 UUID v4 키를 생성하고 네트워크 재시도에 같은 키를 유지하도록 구현한다.
- [ ] 키 보존 만료와 확정된 실패·고아 임시 파일 정리의 상호작용을 통합 테스트한다.

시작 전 질문:

- 처리 중 같은 키에는 `202 Accepted`와 결과 조회 URI를 사용할 것인가, `409`와 `Retry-After`로 같은 POST 재시도를 안내할 것인가?
- 서버 요청 지문은 파일 바이트 SHA-256과 정규화 확장자로 충분한가? 원본 파일명도 포함할 것인가?
- 멱등키와 성공 결과의 보존 기간은 얼마인가?
- 서버 저장 deadline, lease 시간, `Retry-After`, FE 전체 대기 시간은 각각 얼마인가?
- 결과 조회 API를 제공한다면 공개 식별자와 접근 범위는 무엇인가?

중단 규칙: 처리 중 HTTP 계약·요청 지문·보존 기간이 확정되기 전에는 멱등성 테이블과 FE 재시도를 구현하지 않는다.

완료 기준: 응답 유실 뒤 같은 논리적 업로드를 재시도해도 중복 파일이 생기지 않고, FE 재시도 포기는 서버 저장 상태를 임의로 실패 처리하지 않는다.

## 11. ADR 0016 — 정책 집합·allowlist 전환 결정

- [ ] `proposed` ADR 0016의 결정 전 질문을 사용자 답변으로 닫는 질문 문서를 작성한다.
- [ ] 답변을 ADR·API 계약·데이터 모델 방향에 반영한다.
- [ ] shadow 평가의 측정 항목·기록 방식·복귀 기준을 문서로 확정한다.

시작 전 질문:

- 미등록 확장자를 기본 허용하면 안 되는 제품·규제 요구가 실제로 있는가?
- GLOBAL 강제 차단을 ORGANIZATION·USER 범위가 해제할 수 있는가?
- 정책 집합이 없는 대상의 기본 mode는 무엇인가?
- allowlist의 소유자·승인자는 누구이며, 허용 형식 변경을 어떻게 승인하는가?
- shadow 평가 기간과 최대 허용 거부율은 얼마인가?
- 기존 완료 파일을 계속 제공한다는 정책을 유지하는가?

중단 규칙: 하나라도 미결이면 policy-set 스키마·scope API·실제 allowlist 차단을 구현하지 않는다. 이 작업은 즉시 전역 allowlist 전환을 금지한다.

완료 기준: 전환 조건과 우선순위가 ADR에서 accepted로 확정되고, 구현 범위가 명확한 다음 작업으로 분해된다.

## 12. ADR 0016 — 정책 집합·allowlist·shadow 평가 구현

- [ ] mode별 정책 판정, scope 우선순위, 전역 강제 차단, 신규 업로드만 적용, denylist 복귀의 도메인 테스트를 작성한다.
- [ ] 정책 집합·정책 항목·적용 관계·설명 가능한 판정 결과를 구현한다.
- [ ] 기존 전역 denylist와 새 allowlist의 shadow 결과를 기록하고, 승인된 범위에만 단계 적용한다.
- [ ] 정책 변경 감사·오류 코드·FE 안내가 새 판정 결과와 연결되는지 통합 테스트한다.

시작 전 질문: 작업 11의 모든 질문과 ADR 채택이 완료됐는지 확인한다. 미완료면 작업 11로 돌아간다.

완료 기준: 정책 집합의 mode를 혼합하지 않고, 승인된 적용 범위에서 신규 업로드의 allowlist 결과와 shadow·복귀 근거를 확인할 수 있다.
