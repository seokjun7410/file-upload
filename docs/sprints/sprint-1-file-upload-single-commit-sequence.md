# 스프린트 1 단일 커밋 작업 순서

> 상태: 구현 전 작업 순서
>
> 기준 문서: [스프린트 1 API 계약](sprint-1-file-upload-api.md), [스프린트 1 FE/BE 구현 완료 체크리스트](sprint-1-file-upload-checklist.md), [스프린트 1 확장자 차단 정책](sprint-1-file-upload-extension-policy.md)

## 1. 문서의 목적

이 문서는 스프린트 1의 파일 업로드 확장자 차단 수직 슬라이스를 하나의 기능 커밋으로 완성하기 위한 작업 순서를 정의한다. 구현 중간의 Red 테스트와 로컬 검증은 허용하지만, 최종 Git 커밋은 아래 범위의 변경을 모두 포함한 하나의 커밋으로 만든다.

## 2. 단일 커밋 범위

최종 커밋에는 다음 변경만 포함한다.

- 고정·커스텀 확장자 정책의 도메인 모델, 저장소, 정책 서비스
- 고정 확장자 초기화와 DB 저장·조회·변경·삭제 처리
- API 계약에 맞는 요청·응답 DTO 또는 record, 오류 처리, `@RestController`
- 서버 생성 파일명 기반의 파일 저장과 서버 측 확장자 차단
- `Model`을 사용하지 않는 Thymeleaf 페이지와 Axios 기반 정책·업로드 화면
- 기존 `ExampleEntity`, `ExampleRepository`, `ExamplePageController`, 예제 템플릿과 관련 테스트 제거
- 위 동작을 검증하는 도메인·JPA·REST·multipart·페이지 테스트

다음 변경은 이 커밋에 포함하지 않는다.

- API 계약의 URL, 메서드, 상태 코드, JSON 필드명 변경
- MIME 타입·파일 내용·악성코드 검사
- 인증·인가, 사용자별 정책, 파일 목록·다운로드·이력
- 외부 오브젝트 스토리지와 대용량 업로드 최적화
- 별도 리팩터링이나 스프린트 범위 외 UI 개선

## 3. 구현 전 준비

- [ ] `feat/file-upload-extension-policy` 기능 브랜치의 작업 트리가 깨끗하다.
- [ ] API 계약, 스프린트 요구사항, 완료 체크리스트를 읽었다.
- [ ] 구현 중 API 계약이 변경되어야 하는 요구가 발견되면 코드를 진행하지 않고 API 문서를 먼저 갱신한다.
- [ ] 허용된 파일의 저장 위치와 서버 생성 파일명 정책을 애플리케이션 설정으로 정한다.
- [ ] 확장자 없는 파일은 허용하고 서버 생성 파일명으로 저장한다는 권장 정책을 적용한다.

## 4. 구현 순서

### 1단계. 실패하는 행동 테스트를 먼저 작성한다

- 도메인 테스트로 고정 확장자 7개, 초기 `blocked: false`, 정규화, 길이, 중복, 최대 200개 규칙을 고정한다.
- REST MockMvc 테스트로 API별 성공 응답, 상태 코드, 오류 JSON을 고정한다.
- multipart 테스트로 고정·커스텀 차단, 허용 저장, 차단 파일 미저장을 고정한다.
- 페이지 테스트로 루트 페이지의 정상 렌더링과 서버 `Model` 미사용을 고정한다.
- 테스트를 실행해 실패 원인이 미구현 기능임을 확인한다.

### 2단계. 예제 기능을 신규 화면의 빈 자리로 전환한다

- 기존 예제 엔티티·저장소·컨트롤러와 `POST /examples` 흐름을 제거 대상으로 분리한다.
- 루트 페이지는 Thymeleaf 템플릿을 반환하는 최소 페이지 처리만 담당하게 한다.
- 정책과 업로드 데이터는 페이지 요청의 `Model`에 넣지 않고 브라우저의 Axios 호출로 조회하게 한다.

### 3단계. 정책 도메인과 영속성을 구현한다

- 고정 확장자별 차단 상태와 커스텀 확장자를 각각 저장할 수 있는 모델과 저장소를 추가한다.
- 애플리케이션 최초 실행 시 고정 확장자 7개를 준비하고 재실행 시 기존 상태를 덮어쓰지 않는다.
- 입력 확장자를 앞뒤 공백 제거 후 소문자로 정규화하는 단일 규칙을 둔다.
- 커스텀 확장자의 빈 값·20자 초과·중복·200개 초과를 저장 전에 거부한다.
- 고정 확장자는 커스텀 목록에 저장하지 않도록 정책 서비스에서 차단한다.
- 정책 조회, 고정 상태 변경, 커스텀 추가·삭제, 업로드 차단 판정을 정책 서비스의 책임으로 둔다.

### 4단계. REST API와 오류 응답을 연결한다

- API 경로에 `/api/v1`을 적용한다.
- 정책 조회·고정 상태 변경·커스텀 추가·삭제·파일 업로드를 API 계약의 HTTP 메서드로 연결한다.
- 성공 응답은 계약된 JSON과 상태 코드로 반환한다.
- 빈 파일·잘못된 요청·없는 정책·중복·최대 개수 초과·차단 확장자를 공통 오류 형식으로 변환한다.
- 차단 업로드는 `422`, `BLOCKED_EXTENSION`을 반환하고 파일 저장을 호출하지 않는다.
- API 컨트롤러에서 Thymeleaf view, `Model`, redirect를 사용하지 않는다.

### 5단계. 파일 저장을 정책 판정 뒤에 연결한다

- multipart의 `file` 필수를 검증한다.
- 원본 파일명에서 확장자를 서버가 추출하고 동일한 정규화 규칙을 적용한다.
- 정책 서비스가 차단으로 판정하면 저장 경로에 접근하지 않고 오류를 반환한다.
- 허용된 파일만 설정된 저장 위치에 서버 생성 파일명으로 저장한다.
- 저장 성공 시 계약된 파일명과 완료 메시지를 `201 Created`로 반환한다.

### 6단계. Thymeleaf와 Axios 화면을 구현한다

- Thymeleaf 템플릿에는 화면 구조, 입력 요소, 메시지 영역만 둔다.
- 페이지 진입 시 Axios `GET`으로 고정·커스텀 정책을 조회한다.
- 고정 확장자 체크/해제는 `PATCH`, 커스텀 추가는 `POST`, 삭제는 `DELETE`로 처리한다.
- 파일 업로드는 `FormData`의 `file` 필드로 `POST /api/v1/files`를 호출한다.
- 성공 응답과 `400`, `404`, `409`, `422` 오류의 `message`를 화면에 표시한다.
- 정책 변경 후 화면 상태를 API 응답 또는 재조회 결과로 갱신하고, 새로고침 시 항상 서버 상태를 다시 읽는다.

### 7단계. 구현 테스트를 Green으로 만든다

- 도메인 테스트를 먼저 통과시킨 뒤 JPA 저장·조회 테스트를 통과시킨다.
- REST MockMvc 테스트로 요청 본문, multipart 필드, 응답 JSON과 상태 코드를 검증한다.
- 차단 파일의 미저장 여부와 허용 파일의 실제 저장 여부를 임시 저장 위치로 검증한다.
- 정책 변경 직후 별도 업로드 요청에 변경된 정책이 적용되는지 검증한다.
- 페이지 테스트와 전체 테스트를 통과시킨다.

## 5. 커밋 직전 검증 순서

아래 순서를 지키고 하나라도 실패하면 커밋하지 않는다.

1. `./gradlew test`로 전체 자동화 테스트를 실행한다.
2. API 경로·상태 코드·응답 JSON을 API 문서와 대조한다.
3. 브라우저에서 정책 조회·변경·추가·삭제·파일 업로드를 수동 확인한다.
4. 차단 파일이 저장되지 않고 허용 파일이 저장되는지 저장 위치에서 확인한다.
5. `git diff --check`로 공백 오류를 확인한다.
6. `git status`로 문서 외 범위의 미추적·미커밋 파일과 의도하지 않은 변경을 확인한다.
7. staged diff를 검토해 단일 커밋 범위를 벗어난 변경이 없는지 확인한다.

## 6. 커밋 기준

- 커밋 메시지: `feat: implement file upload extension policy`
- 정책 도메인, REST API, 파일 저장, Thymeleaf·Axios 화면, 테스트, 예제 제거가 하나의 커밋에 함께 포함되어야 한다.
- 테스트 실패, API 계약 불일치, 차단 파일 저장, `Model` 기반 API 응답이 하나라도 있으면 커밋을 보류한다.
- 커밋 후 체크리스트의 각 항목에 코드·테스트·수동 확인 근거를 기록한다.
